# 卡片笔记应用 —— 架构与实现方案

> 产品名：Folio（中文名「页」，2026-10-25 定），代码、crate、目录统一用 `folio`；bundle identifier 暂用占位 `dev.folio.app`，正式值待定（见第 10 节第 1 项）
> 日期：2026-10-21 · 状态：已评审两轮（2026-10-23）；CRDT 已定为 Loro（[ADR 0001](adr/0001-crdt-choice.md)）

## 0. 目标与非目标

**目标**

1. **跨端**：一套代码覆盖 macOS / Windows / Linux / iOS / Android（Tauri 2）。
2. **数据库为真相源**：不以 Markdown 文件为存储；本地 SQLite，离线优先。
3. **远程同步**：多设备离线编辑后自动合并，不出冲突副本；可选端到端加密（E2EE）。
4. **Heptabase 式卡片笔记**：卡片独立存在，可放入多块白板；白板上排布、连线、分区。
5. **保留大纲笔记的好处**：双链 `[[ ]]`、块引用、反向链接、日记、标签。
6. **插件能力**：开源后社区可以写插件扩展功能，且插件在所有平台（含 iOS）上安全可用。

**非目标（至少 1.0 之前）**

- 与 Logseq Markdown 图谱双向实时兼容（tine 的路线）——只做**导入**和**导出/镜像**。
- 多人实时协作 UI（光标、在线状态）——架构上支持（CRDT），但不做产品功能。
- Datalog 查询语言。
- 兼容 Logseq / Obsidian 的插件 API（只提供移植指南，不做兼容层）。
- 追求新奇的交互创新（如历史版本时光机、画线建立联系）——先把基础记录做好，这些以后再说。

### 0.1 产品原则（按优先级，冲突时排前者优先）

做这个项目的出发点：现有笔记软件的更新节奏由别人掌控、bug 多且修得慢、订阅价格高。所以它的价值不在“新”，而在**可靠、自己能修、数据和成本自己掌控**。

1. **数据安全第一**：任何功能、任何优化都不能以丢数据为代价，也不能让笔记被别人读到。4.5 节建模规则、5.3 压缩规则、5.4 恢复规则、5.6 安全与隐私清单都是这一条的体现。面向他人发布之前，5.6 的清单必须全部完成。
2. **先把基础记录做好**：打字、列表、粘贴、撤销、输入法、搜索、链接这些每天都用的东西，优先级高于任何新功能。
3. **可靠、修得快**：每个 bug 先写成能复现的测试再修，修过的问题不再回来；出问题时能一键导出诊断信息（不含笔记内容）；CI 自动构建各平台安装包、自动更新推送，修复当天就能装到桌面和安卓设备上；iOS 受苹果审核限制，自用可通过 TestFlight 内部测试当天安装，公开版本需等审核（见 7.2）。
4. **熟悉、顺手，不追求新奇**：布局和快捷键贴近主流笔记软件，降低迁移成本；功夫花在手感和一致性上，而不是视觉噱头。
5. **全球化**：面向全球用户，所有语言的排版和输入都是一等公民，界面国际化从第一天做起（见 0.2）。
6. **低成本、可自托管**：没有订阅费；同步服务器只做中转，个人用一台便宜的服务器或云服务免费额度即可。
7. **数据属于用户**：开源；随时可导出为 Markdown（白板导出为 JSON Canvas），不被锁定。

### 0.2 界面与交互约定

**核心模型（2026-10-23 已定）**
1. **以卡片为中心**：知识的基本单位是卡片，一张卡片表达一个完整的想法。日记是“收件箱”，想法成熟后提炼成卡片，卡片放到白板上组织。
2. **一键提炼成卡片**：在日记里选中一个块（连同子块），一个快捷键就变成新卡片，原位置留下指向卡片的链接。这是连接“记录”和“沉淀”的关键动作，要做得极其顺手。
3. **一个编辑器、一套列表行为**：日记新起一行默认是列表项（大纲），卡片默认是段落（自由文档）；缩进、反缩进、折叠、拖动列表项在两处完全一致。每张卡片可设为“大纲模式”，新起一行默认就是列表项。块引用照常可用（每个块都有稳定 id），但不作为主要组织方式。
4. **日记是连续日记流**：今天在最上面，往下滚动是前几天；顶部日历可跳到任意一天（含未来日期，用于规划）。渲染、懒加载、按需创建和日期 / 时区规则见 5.2a。
5. **打开卡片**：默认在当前窗格开新标签页；`Shift+点击`（卡片库里是 `Alt+点击`，因为 Shift 用于多选）在另一侧窗格打开（分屏，见 8.7）。
6. **视觉风格：安静的纸面感**：留白多、行距宽、界面元素尽量少、无多余边框，正文排版舒展。
7. **正文字体（2026-10-23 已定）**：中文**思源宋体**（Source Han Serif / Noto Serif SC），英文 **Source Serif 4**。两者同属 Adobe 的 Source 字体家族，思源宋体的拉丁字母即以 Source Serif 为基础，中英混排最协调。界面文字（侧栏、菜单、按钮）用系统无衬线字体。其余排版参数的起点见 `design/research/ui-research.md` 第 9 节，可在 `spike/web` 的排版试验页里继续微调。
   - **分发方式（2026-10-23 已定）**：思源宋体简体中文可变字体约 24 MB，Source Serif 4 约 2 MB（含斜体）。
     - **桌面端**：两款字体随安装包内置，装好即是最终效果。
     - **手机端**：安装包不含这两款字体，首次启动时按需下载；下载完成前正文先用系统字体（衬线优先，没有则用系统默认字体），下载后无缝切换，不需要重启。
     - **许可**：两款字体都是 SIL Open Font License 1.1，随应用分发时必须附带许可文本（放进安装包的许可目录，并在“关于”页面列出），不得单独出售字体；手机端下载时同样附带许可文本。
     - 实现要点：字体放在应用数据目录，通过自定义协议提供给前端（与 4.6 节的文件读取方式一致），用 `@font-face` 加载；下载支持断点续传和完整性校验（SHA-256）；移动网络下先提示再下载，用户也可以在设置里稍后下载或删除；下载失败不影响使用，只是继续用系统字体。
   - 按同类软件惯例，正文样式开放给用户切换：衬线（默认）/ 无衬线（系统字体）/ 等宽。

**布局（2026-10-23 已定）**
- 桌面：左侧栏 + 主编辑区（标签页、可分屏）+ 右侧面板。
- **左侧栏**（`Mod+\` 收起）：搜索 / 命令面板、新建卡片；主入口：日记、卡片库、白板；置顶（可拖动排序）；白板目录（文件夹树）；标签（常用标签，点开为带该标签的卡片）；最近打开；底部：回收站、设置、同步状态。
- **右侧面板**（**默认收起**，记住上次状态）：内容随当前标签页变化。卡片：目录、属性与标签、反向链接、未链接引用、所在白板（以后加 AI 相关卡片）；日记：当天提到的卡片、未完成任务。各部分可单独折叠。面板收起时，卡片底部始终显示反向链接。
- **标签页**：可以是日记、卡片、白板或卡片库，各自有后退 / 前进历史；中键或 `Mod+点击` 后台打开，`Mod+W` 关闭，可手动固定，重启后恢复。日记**不固定**，和其他标签页一样可关闭。**同一张卡片再次打开时切到已有标签页**，分屏时例外（允许左右对照同一张卡片）。`Shift+点击` 链接在另一侧窗格打开（分屏是第二个编辑区，不同于右侧面板，见 8.7）。
- 手机：以“记录”和“浏览”为主——底部 4 个入口（日记、卡片、白板、搜索）+ 悬浮的“快速记录”按钮；没有侧栏和右侧面板，反向链接放在卡片底部；白板以浏览为主（双指缩放、点开卡片），不追求完整的白板编辑。
- **手机版式第一批（2026-10-25）** ✓：宽度 ≤ 720px 时不显示侧栏和标签栏，顶部一条栏（从别处打开的页面有“返回”，按打开顺序退回；入口页右上角是设置），底部四个入口（日记、卡片库、白板、搜索），日记和卡片库右下角浮着“快速记录”；一个窗格最多保留 8 个打开的页面，最久没用的先关。设置铺满全屏，分区横向排开。触摸屏（`hover: none` 且 `pointer: coarse`，平板也算）：长按代替右键（`shell/longPress.ts`，按住 0.5 秒不动发出 `contextmenu`，抬手不再触发点击；文本框和编辑器里保留系统的长按选字）；卡片库里长按是选中卡片、进入多选；原来悬停才出现的按钮一直显示；输入框字号 16px（iOS 小于 16px 会放大页面）；菜单旁的快捷键提示不显示；屏幕键盘为编辑器弹出时键盘上方一排按键：取消缩进、缩进、待办（切换状态）、`[[`、`#`、`/`、插入图片（相册或拍照）、撤销、重做、上移、下移、折叠、`((`，可左右滑动，收起键盘固定在最右边（2026-10-29，参照 Logseq 手机端；缩进、待办、撤销等发出对应按键给编辑器，和键盘操作完全一致；`[[` `#` `/` `((` 按打字处理，自动配对和候选菜单照常弹出，`#` `/` 前面不是空格时先补一个空格；按下时阻止失焦，键盘不收起；抬手且手指没移动才执行，滑动按键栏不会误触）；键盘收起（包括按键盘自带的收起键、或接了实体键盘）时即使编辑器仍有焦点，底部也换回四个入口（2026-10-28；键盘高度按 iOS 的“页面被遮住”和安卓的“页面被压矮”两种方式都能识别）；打字时光标始终留在键盘按键栏上方约 72px 的位置，换行、自动折行、拼音输入中都会跟着滚动；白板单指拖动平移、双指缩放、长按出菜单，菜单不超出屏幕，缩放栏移到右上角。验证：WebKit 以 iPhone 13 尺寸和触摸模拟走通。尚未做：真机、安全区域实测、安卓原生层、手势（横滑等）。
- **手机的安全区域**（系统状态栏、底部手势条 / 导航键、刘海、软键盘占用的区域）：设计稿只画界面本身，不包含这些区域的空白；实际留空由各平台在运行时决定，并且**同一块区域只由一层负责**，避免双倍留白：
  - **iOS**：由网页负责，用 CSS `env(safe-area-inset-*)`（页面设 `viewport-fit=cover`），例如底部导航栏的下内边距加上 `env(safe-area-inset-bottom)`。
  - **安卓**：由原生层负责。Android WebView 的 `env(safe-area-inset-*)` 不可靠（tine 记录：WebView 124 在 Android 15 / API 35 上一律返回 0），而 Android 15 起应用默认全屏绘制到系统栏后面。做法：`MainActivity` 调用 `enableEdgeToEdge()`，监听 `WindowInsets`，取系统栏 + 刘海的尺寸给整个 WebView 加边距；底部边距取“导航栏高度”和“软键盘高度”中的较大值，键盘弹出时页面自动让位（WebView 不一定会因键盘缩小）。网页里的安全区域变量此时统一为 0。参考 tine 的 `src-tauri/gen/android/app/src/main/java/page/tine/app/MainActivity.kt` 与 `src/systemInsets.ts`。
  - 前端统一使用 `--system-inset-top/right/bottom/left` 这组变量，启动时按“当前由谁负责”设定：iOS 取 `env()` 的值，安卓原生应用中为 0，浏览器中取 `env()` 的值。
  - 安卓上 WebView 外露出的系统栏区域要设成相邻界面的颜色（顶部同页面底色，底部同导航栏底色），并随浅色 / 深色切换，否则会出现颜色不一致的色带。

**输入与快捷键**
- 快捷键沿用主流约定，可自定义：`Mod+K` 搜索/命令面板，`Mod+N` 新卡片，`Mod+Z` / `Mod+Shift+Z` 撤销/重做，`Mod+Enter` 切换任务状态，`Tab` / `Shift+Tab` 缩进。
- 编辑器支持 Markdown 式输入：`#` 标题、`-` / `1.` 列表、`[]` 任务、```` ``` ```` 代码块、`>` 引用、`[[` 链接、`((` 块引用、`/` 斜杠菜单。
- 粘贴保留结构（从网页、Markdown、其他笔记软件粘贴都尽量还原标题和列表）。
- 全局快速记录：系统级快捷键唤出小窗，写一句就进今天的日记，不打断当前工作。

**反馈与手感**
- 操作即时生效；不弹“确定删除吗”这类确认框，改为“已删除 · 撤销”的提示条；所有操作都可撤销。
- 动画 ≤ 200 ms，可以随时被打断；尊重系统的“减少动态效果”设置。
- 同步状态只用一个轻量指示表达；永远没有冲突对话框（CRDT 自动合并）；离线照常使用。
- 性能预算（作为验收标准）：桌面启动到可输入 < 1 s；打开卡片 < 50 ms；按键处理 p95 < 16 ms（中端手机）；搜索 < 100 ms；白板开启 LOD 时 ≥ 55 fps。

**排版与多语言**
- 英文：弯引号与破折号、合适的行长与字距、OpenType 特性（连字、数字样式）、断词。
- 中日韩：合适的行高、标点挤压、避头尾；中日韩输入法在编辑器里组字、选词、远端更新到达时都不出错。
- 混排：中西文之间的间距；按文字分别选用合适的字体并设置回退。
- 国际化：界面文字全部抽成多语言资源（首批中、英），日期、数字、一周起始日跟随用户地区；从右到左书写的语言在布局上预留，暂不实现。

**设计系统**
- 颜色、间距、字号、圆角、阴影、动效曲线统一定义为 token；明暗两套主题，跟随系统。
- 组件底层用无样式的可访问组件库 Base UI，外观完全自己做。
- 可访问性：全键盘可达（白板上也能用方向键在卡片间按位置移动）、清晰的焦点样式、足够的对比度、读屏标签。

### 0.3 AI 原生（规划，细节待讨论）

目标：笔记从一开始就能沉淀为 AI 可用的个人知识库。**底层从 M0 就按“AI 能读、能精确引用、能安全写入”来设计，AI 功能按层级逐步上线**，不违背 0.1 “先把基础记录做好”。

| 层级 | 内容 | 时间 |
|---|---|---|
| 数据底子 | 块有稳定 id（可精确引用）；链接存 id（知识图谱是结构化数据）；每个块和卡片记录**出处**（人写 / AI 生成及模型 / 导入）；所有读写走同一套语义 API，供插件、MCP、应用内 AI 共用 | M0–M1 |
| 对外接口 | **MCP 服务**：让任何支持 MCP 的 AI 工具直接使用知识库。先只读（搜索、读卡片、反链、按标签查询），后加写入（经用户审核）。跑在应用进程内，或由命令行工具转发给正在运行的应用，以保持单一写入者。**安全**（评审补充）：MCP 服务一旦开启，本机任何程序都可能读取全部笔记，所以**默认关闭**；只监听本机；连接需要令牌（在设置中生成、可随时吊销），新客户端首次连接需在应用内确认；按工具分级授权（只读 / 写入），写入工具的修改走“建议”流程并标注出处 | 只读：M2；写入：M3 之后 |
| 检索 | 以块为单位的向量索引 + 现有全文搜索 = 混合检索；向量放在 index.db，属于派生数据、可重建；在设备上计算（端到端加密下服务器无法建索引） | M3 之后 |
| 应用内能力 | 围绕“沉淀”：从日记提炼卡片、建议链接与标签、定期回顾、带块级引用的问答；AI 的修改以“建议”形式出现，确认后才写入，标注出处、可撤销 | M6 起 |
| 模型与隐私 | 用户自带 API 密钥，或使用本地模型；不强制订阅；发往云端模型的内容范围在发送前明确告知 | 随功能上线 |

待讨论：AI 功能优先级、模型与嵌入模型选择、MCP 工具清单与权限、建议/审核的交互形式。

## 1. 从两个项目吸取什么

### 1.1 Logseq（DB 版）

| 借鉴 ✅ | 出处 | 在本项目里怎么用 |
|---|---|---|
| DB 是唯一真相源，Markdown 只是派生镜像 | ADR 0016 | `export/mirror` 模块单向输出 md，永不回读 |
| **单一数据所有者**：只有 worker 拥有图谱事实，UI 只拿纯数据 | ADR 0022 | Rust core 拥有持久化与索引；前端只持有“正在编辑的卡片”的 Loro 副本 |
| 批量操作原子提交 | ADR 0005 | 一个用户动作 = 一个 Loro commit + 一个 SQLite 事务 |
| 同步收敛校验（checksum） | ADR 0006 | 空闲时比较版本向量 + 状态哈希，不一致则报警并全量重拉 |
| 删除分两类：内容进回收站，结构性元数据硬删 | ADR 0009 | 卡片/白板软删除（`deleted_at`），标签定义等硬删 |
| 同步做**模拟与回放测试**，每个线上 bug 写成确定性复现 | ADR 0008 | `folio-sync` 自带多 peer 随机模拟器 |
| 客户端待同步操作、同步元数据放在 SQLite 表里 | ADR 0015 | `sync_state` / `outbox` 表 |
| 可选 E2EE | ADR 0003 | 服务端只存密文 blob |
| 插件用 TypeScript 写、能提供 UI（斜杠命令、面板、宏渲染），生态起得快 | `libs/`（`@logseq/libs`） | 同样用 TS 写插件，同样能扩展 UI，但走声明式 UI + 沙箱 iframe |
| SDK 自带给 AI 用的开发指南 | `libs/SKILL.md`、`libs/guides/AGENTS.md` | SDK 附 `AGENTS.md` 与完整类型，方便用 AI 写插件 |

| 规避 ❌ | 原因 | 本项目的做法 |
|---|---|---|
| 自研“服务端定序 + 客户端 rebase” | ADR 0002/0004/0010/0011/0012 反复重构，复杂度极高 | 用 CRDT（Loro），合并在数据结构层面自动完成，服务端只做中继 |
| 撤销/重做与同步纠缠 | 需要语义逆操作持久化、rebase 后改写 | Loro `UndoManager`：只撤销本地操作，天然不受远端编辑影响 |
| DataScript 全量载入内存 | 大图谱慢、占内存 | 按需加载单张卡片文档；全局查询走 SQLite 索引 |
| ClojureScript 小众栈 | 贡献者少，AI 辅助效果差 | TypeScript + Rust |
| 双外壳（Electron + Capacitor） | 两套原生集成 | 只用 Tauri 2 |
| 插件 API 直接暴露内部数据结构 | 迁到 DB 版时插件大面积失效，只能另写新的属性开发指南 | 插件只看到版本化的语义 API，内部模型可以自由重构 |
| 插件 iframe 能拿到较多宿主能力，安全边界弱 | 社区插件等于拥有整个库的读写权 | 能力需在 manifest 声明、用户授权，所有调用经宿主中转 |

### 1.2 Tine

| 借鉴 ✅ | 出处 | 在本项目里怎么用 |
|---|---|---|
| **纯 Rust 核心，不依赖 GUI，可单测；Tauri 层只是薄 IPC** | ADR 0003 | `folio-core` / `folio-store` 等 crate 无 Tauri 依赖；`src-tauri` 只做封装 |
| **前端拥有实时编辑树**，按键不跨 IPC，防抖保存 | ADR 0002 | 前端 Loro 文档直接编辑，增量 update 以二进制批量送 Rust |
| **唯一写入通道** | ADR 0012 | 前端只有 `persistence.ts` 能调用写命令；Rust 只有 `Store::commit` 能写库 |
| 派生缓存用单一代数（generation）失效，宁可全量失效也不陈旧 | ADR 0014 | 索引库可整体重建；增量更新失败就回退为重建该卡片 |
| 数据安全不变量：原子写、回收站、启动快照、一键恢复 | ADR 0007/0062 | SQLite WAL + 定时 `backup` 快照 + 回收站 |
| 崩溃不丢未保存草稿 | ADR 0061 | 每次 Loro update 在 ~300ms 内落库；前端崩溃也能从库恢复 |
| 视口外懒渲染 | ADR 0008 | 白板上视口外的卡片不挂载编辑器，只渲染静态预览 |
| 块身份 ≠ 渲染实例 | ADR 0013 | 同一卡片在多处显示时，编辑焦点按“surface”区分 |
| 前端有 mock/浏览器后端 | ADR 0016 | `platform/` 抽象，浏览器里也能跑 UI，便于开发和未来 Web 版 |
| 移动端打包经验（Android/iOS、fastlane） | `docs/ANDROID-RELEASE.md` 等 | 直接参考配置 |
| 插件**能力词表封闭**、只含宿主代办的语义操作；插件写入走与用户编辑相同的持久化/撤销路径 | ADR 0045 | 插件 API 设计的第一原则 |
| 能力边界在所有平台一致，从一开始就满足苹果审核 4.7.2（插件不得暴露原生 API） | ADR 0052 | iOS 也能开放插件，不需要“桌面特权层” |
| 插件设置声明式，由宿主渲染；主题是独立的纯数据包 | ADR 0046 | 同样拆分“主题”与“插件”两种包 |
| 插件 manifest 显式声明支持的平台，未声明即不在该平台运行 | ADR 0047 | 同样做法 |
| 注册表：不可变摘要、源码与许可证必填、自动审计、签名吊销 | ADR 0045 | 社区插件仓库照此设计 |

| 规避 ❌ | 原因 |
|---|---|
| 与 Markdown 文件逐字节兼容 | 大量精力花在格式兼容（ADR 0004/0040），且无法做好同步 |
| 靠 Syncthing + 冲突文件合并 | 冲突只能事后处理（ADR 0020），CRDT 从根上避免 |
| SolidJS | 生态里没有成熟的白板库，编辑器生态也弱于 React |
| 白板列为非目标 | 这是本项目的核心 |
| 插件只能是 Wasm、完全不能提供 UI | 安全但门槛高、表达力弱，社区难以起量。本项目改为：插件用 TS 写，跑在 QuickJS-wasm 沙箱里；UI 用声明式组件，必要时用沙箱 iframe |

### 3.1 职责边界（关键不变量）

1. **Rust `folio-store` 是唯一持久化写入者。** 任何写入（编辑、导入、同步、恢复）最终都走 `Store::apply_update(doc_id, bytes, origin)`。
2. **前端只为“打开中的文档”持有 Loro 副本。** 按键只改前端副本；`persistence.ts` 以 ~300ms 防抖把增量 update（二进制）送到 Rust。
3. **远端变更由 Rust 推给前端。** 同步拉到 update → Rust 导入并落库 → 若该文档在前端打开，发 `doc-updated` 事件，前端 `import` 同一份 bytes。CRDT 保证两边收敛，无需锁。
4. **全局读（搜索、反链、卡片列表、标签表）只走 `index.db`**，从不加载全部文档。
5. **`index.db` 可随时删除重建**；任何提取失败，回退为该文档全量重建，绝不留下陈旧索引。

## 4. 数据模型

### 4.1 文档划分（每个文档 = 一个 Loro Doc）

| 文档类型 | doc_id | 内容 |
|---|---|---|
| `workspace` | 固定 `ws` | 白板目录树（LoroTree）、标签定义与属性 schema（Map）、**需要跨设备一致的设置**（如正文样式、快捷键方案、插件同步数据）、已永久删除列表 `purged` |
| `card` | UUIDv7；日记为 `journal:2026-10-21`（确定性 id） | `meta`(Map) + `body`(富文本，loro-prosemirror 结构) |
| `board` | UUIDv7 | `meta`、`items`(Map)、`edges`(Map)、`sections`(Map) |

> **设置分两类**（评审补充）：跨设备一致的放 workspace 文档并同步；只属于本机的放 `store.db` 的 `local_settings` 表、不同步，例如字体是否已下载、窗口大小与位置、右侧面板开关、打开的标签页、移动网络下是否自动下载、本机 peer id 以外的设备信息。新增一项设置时先决定它属于哪一类。

> **日记用确定性 id**：两台设备离线时都创建了“今天”的日记，同步后是**同一个文档**，不会出现两篇。这要求文档的根结构按 4.5 节用 mergeable 容器创建，否则合并后一台设备写的内容会整段丢失（评审时已复现）。

**为什么每张卡片一个文档，而不是整个库一个文档？**
- 按需加载，内存与打开速度与库大小无关；
- 同步粒度细，只传有变化的文档；
- 单文档历史增长可控，可单独做浅快照（shallow snapshot）压缩。

### 4.2 Card 文档结构

```
card
├─ meta: Map
│   ├─ kind: "note" | "journal"
│   ├─ editor_mode: "document" | "outline"   （新起一行默认段落还是列表项；日记固定为 outline，见 0.2）
│   ├─ title: string            （同时作为 [[链接]] 名）
│   ├─ created_at, deleted_at?
│   ├─ tags: Map<tag_id, Map<prop_id, value>>   （Heptabase 式：标签即数据库；内层 Map 用 ensureMergeableMap 创建，见 4.5）
│   ├─ icon?, color?
│   └─ source: "human" | "ai:<model>" | "import:<来源>"   （出处，见 0.3）
└─ body: ProseMirror 树（由 loro-prosemirror 映射）
    节点：paragraph / heading / bulletList / taskItem / code / image / embed / ...
    每个块级节点有 attrs.bid（UUIDv7，块引用的锚点）和可选的 attrs.source（出处，默认人写）
```

- **提炼成卡片**（0.2）涉及两个文档：先创建新卡片并写入块的内容（块 id 随内容一起迁移，已有的块引用继续有效——块引用按 `bid` 解析，见下），再把日记里的原块替换为指向卡片的链接。两步不在同一个事务里；如果中途崩溃，最坏结果是多出一张没被链接的卡片，不会丢内容。撤销时两步一起回退（5.1 跨文档撤销）。
- 链接语法在编辑器中是**节点/Mark**，不是文本解析：
  - 卡片链接 `cardLink{card_id}`（显示时取目标卡片当前标题，改名不需要回写引用——这是 DB 方案相对 md 的大优势）
  - 块引用 `blockRef{bid, card_hint?}`：**按 `bid` 全局解析**，`card_hint` 只是上次所在卡片的提示，用来加速和消歧。块被移动到别的卡片（提炼成卡片、拖到另一张卡片）时 `bid` 不变，引用自动跟过去。
  - **块 id 的全局唯一**（评审补充）：4.5 / 5.1 的规范化只能保证同一文档内不重复。跨文档的重复来自复制粘贴，所以**粘贴到另一张卡片时重新生成块 id**（剪切后粘贴视为移动，保留原 id）。并发编辑仍可能在极少数情况下产生跨卡片重复，索引要能容忍并检测：解析时优先选 `card_hint` 所在的那份，其余标记为“重复”，在界面上提示。
  - 标签 `tag{tag_id}`

### 4.3 白板（Board，2026-10-25 定稿）

**对照**（吸收的精华 → 本方案）
- **Heptabase**：卡片只存一份，白板引用卡片，同一卡片可在多块白板；卡片在白板上直接可编辑；从卡片边缘拉出连线、线上可写字；框选后 ⌘G 建小节，小节标题缩小时仍清楚，拖小节带着里面的卡片走；右侧栏的卡片库可以把卡片拖进白板；文字元素、思维导图。→ 全部采纳（思维导图见下文“思维导图”）。
- **Obsidian Canvas / JSON Canvas 1.0**：节点 `text/file/link/group`，连线带 `fromSide/toSide`、`toEnd` 默认箭头、可选标签与颜色；颜色是 6 个预设（红橙黄绿青紫）或十六进制；数组顺序即层级。→ 字段与之对应，**可导出为 .canvas**，换到 Obsidian 能直接打开（开放格式，数据不被锁定，0.1 原则 7）。
- **Logseq（tldraw）/ Muse / Scrintal / Kinopio**：白板上放的是笔记本身而不是图形；画图工具（形状、手绘）不是重点。→ 第一版不做自由绘图。

**决定**
- **白板是独立的**（2026-10-25 修订：第一版把白板做成主题的视图，用户要求与日记、卡片库同级）：侧栏“白板”打开白板列表，可以建任意多块；每块白板的列表信息（名称、创建时间、删除标记）在工作区文档的 `boards`，内容在文档 `board:<白板 id>`。与主题互不关联。
- **把卡片放上白板**：分栏时从卡片库把卡片（可多选）拖进白板；或用工具栏的“放入已有卡片”搜索；或在白板上新建卡片。从白板移除只是拿下来，卡片仍在卡片库。第一版在主题下建过的白板（`board:<主题 id>`）会以主题名加入白板列表，内容保留。
- 白板上还有**文字**（自由文字、便签）和**小节**（带标题的框，可着色）。拖小节时带走完全在框内的元素（几何包含，与 Heptabase、Obsidian 一致，不另存归属关系）。
- **连线**：从元素四边的连接点拉到另一个元素；箭头指向终点；双击写标签；可着色。
- **卡片在白板上**：显示标题和正文结构（来自索引的正文文本，按缩进成列表）；**双击就地编辑**（挂载编辑器，同时最多 1 个），Esc 或点空白处结束；工具条里“在标签页打开”。
- 以标签页打开白板（Heptabase 同样以标签页打开白板）；入口：侧栏“白板”（列表页）与侧栏的白板分区、⌘K 的“新建白板”“打开白板列表”。白板列表页和卡片库一样，一个窗口里只开一个。

**数据（`board:<白板 id>`，DocKind `board`；列表在 `ws.boards`）**
```
board
├─ items: Map<item_id, Map>   每个元素一个 Map，只由创建它的设备建一次，字段逐个合并
│     { kind: "card"|"text"|"section"|"mind", card_id?, text?, x, y, w, h, z, color?,
│       parent?, order?, root?, collapsed? }   ← 后四个是思维导图用的
└─ edges: Map<edge_id, Map> { from, to, from_side?, to_side?, label?, color? }
```
- 并发拖动同一元素：x / y 各自 LWW，取较新的位置；一边删除一边移动：删除生效。
- 删除元素时同一次提交删掉连到它的连线；渲染时也忽略端点不存在的连线（另一台设备删了元素）。
- 视口（平移、缩放）只存本机设置，不同步。
- 卡片软删除后，白板上的卡片显示“已在回收站”，恢复后照常。

**交互**：滚轮 / 触控板平移，⌘ + 滚轮或捏合缩放，⌘0 适应窗口；点击选中，Shift 多选，在空白处拖动框选；拖动移动，角点调整大小；Delete 删除选中；⌘G 把选中元素框进新小节；⌘Z / ⇧⌘Z 撤销重做（白板文档自己的撤销历史）；双击空白处新建文字。

### 4.5 CRDT 建模规则（评审补充，必须遵守）

评审中用测试复现了两个“并发创建”导致整块数据丢失的问题（`spike/web/test/review.test.ts`），修复已验证（`review-fix.test.ts`）。规则如下：

1. **可能被多台设备同时创建的子容器，一律用 `ensureMergeable*`**（`ensureMergeableMap` / `List` / `Text` / `Tree` 等）。Map 某个键下用普通方式（`setContainer` / `getOrCreateContainer` / Rust `insert_container`）各自新建子容器时，Loro 视为两个不同容器，合并后只保留一个，另一方写进去的内容全部丢失。`ensureMergeable*` 为“同一父容器 + 同一键 + 同一类型”生成确定的容器 id，两边写的是同一个容器。适用范围：
   - 卡片 `meta.tags` 的内层 Map（两台设备同时给卡片加同一个标签）；
   - workspace 文档里的标签 schema、设置分组、插件同步数据 `plugins.<id>`；
   - **所有卡片正文的根节点**（loro-prosemirror 的根 Map `doc` 下的 `attributes` / `children`）——日记用确定性 id，两台设备离线写同一天日记时会同时创建它。
   - 只由一台设备创建、且键本身唯一的容器（如 `items.<uuid>`）可以用普通方式。
   - 注意 mergeable 容器的语义：删除键只是隐藏子容器，内容仍保留；之后再对同一个键调用 `ensureMergeable*`，旧内容会重新出现。例如移除标签再加回来，旧的属性值会回来。需要“重新开始”时，先清空子容器的内容再删除键。
2. **编辑器绑定要打补丁**：loro-prosemirror 用 `getOrCreateContainer` 创建每个节点的 `attributes` / `children`。在 vendor 进仓库的版本里改为 `ensureMergeableMap` / `ensureMergeableList`（父容器 id 唯一，非根节点改了也不影响行为）。M1 用“两台设备离线写同一天日记”做编辑器级回归测试。
4. **块按身份移动**：正文的块结构存在 **LoroTree**（根容器 `blocks`，**布局 3**，2026-10-24）。每个块级节点（段落、标题、代码块、列表、列表项、引用、分隔线、图片、公式块）是一个树节点，节点的 `data`（LoroMap）存 `nodeName`、可合并的 `attributes`；**文本块**（段落、标题、代码块）另有可合并的可移动列表 `children`，存行内内容（LoroText 与行内节点：卡片链接、块引用、标签、换行、行内公式），容器块的子块就是树节点的子节点。读取时的规则：`data` 里有 `children` 的是文本块，否则看树的子节点。
   - 绑定写入时按块 id 在**整棵树**里找对应节点（无 id 的列表等按类型和出现次序在同一父节点下匹配），位置不对就 `move` 到新父节点和新位置——**跨父节点的移动（缩进、反缩进、拖进别的列表、提炼）保留节点身份**，另一台设备同时对这个块的修改随块一起过去；没用到的节点最后删除。节点类型变化原地改名。
   - Loro 的树保证并发移动不产生环、不重复（两台设备互相把对方移到自己下面时只保留一个有效结构），同父节点下的顺序用分数索引。
   - 布局 2（根 `body` 映射、子节点用可移动列表）只能在同一列表里移动，跨父节点的移动是“删了再建”，并发修改会丢；布局 1（根 `doc`、普通列表）更早。旧文档在 `folio-store` 打开时按 1→2→3 迁移一次；迁移不能在两台设备上对同一文档执行，所以必须在同步（M3）之前完成。
3. **peer id 按“设备 + 进程角色”分配并持久保存**：同一台设备上前端和 Rust 各持一份文档副本，必须用不同的 peer id；同一个 peer id 绝不能被两个同时活跃的副本共用，否则会产生 id 相同、内容不同的操作，文档损坏。也不要每次打开文档都随机生成新 id，否则版本向量会随打开次数无限增长。peer id 存在 `sync_state` 里。前端有两份副本：编辑器用的 `peer.frontend`，语义 API（命令、插件、AI 写入，见 0.3）用的 `peer.api`——绑定会忽略不是它自己发出的本地修改，所以 API 在独立副本上编辑，再把结果导入编辑器的副本，打开的编辑器按“收到远端修改”刷新（M1a 实现，`web/src/api`）。

### 4.6 文件：图片、语音、PDF 等（骨架，细节待细化）

已定的原则：
1. **文件不进 SQLite**，作为普通文件存在工作区的 `assets/` 目录；`store.db` 的 `assets` 表只存元信息。原因：大文件会让数据库和备份膨胀，音视频、PDF 需要按字节范围读取。
2. **按内容寻址**：文件名就是内容的 SHA-256（按哈希前缀分子目录），自动去重；文件不可变，内容变了就是另一个文件。
3. **文档里只存引用**：卡片的图片 / 音频 / PDF 节点、白板的图片 / PDF 元素，属性里只放哈希。
4. **前端经自定义协议读取**：`folio-asset://<哈希>`，由 Rust 读磁盘，支持按字节范围读取（音频拖动进度、大 PDF 翻页即读）。
5. **从文件派生的内容都可重建**：缩略图放缓存目录；PDF 抽取的文字、语音转写的文字进入 `index.db`，供全文搜索和 AI 检索（0.3）。
6. **文件单独同步**，不走 CRDT 增量通道：加密后上传到 S3 兼容的对象存储（5.3）。

**本地部分已实现（2026-10-28，细节见 `design/attachments.md`）**：图片与文件块（`image` 加 `asset/name/mime/size`，新的 `file` 块）；粘贴、拖入、`/` 菜单“图片”“文件”；分块写入 `assets/.incoming/` 再按哈希改名；`folio-asset` 协议（支持 Range）；Apple 设备上 HEIC 转 JPEG；单文件上限 100 MB；`idx.asset_refs` 记引用，无引用 30 天后清理（`assets.orphan_since`，迁移 3）；导出 Markdown 时复制到 `assets/`。

**同步已实现（2026-10-28）**：文件按 1 MiB 分块加密（XChaCha20-Poly1305，块号与是否最后一块绑定在附加数据里，最后一块补齐到 64 KiB 的倍数），服务器上的 id 是文件哈希的 HMAC；存在同步服务器自己的 `<数据库>.blobs/` 目录（没有用 S3 兼容存储），断点续传；下载后校验哈希。独立的 `sync-files` 线程，不拖慢文档同步。电脑下载全部文件，手机只下载用到的（加载不出来的图片、点开的文件、卡片菜单“下载本卡片的全部附件”）。服务器上没有设备再用的文件，所有设备都确认后 30 天删除（`FOLIO_SERVER_UNUSED_FILE_DAYS`，0 不删；见 attachments.md §6）。

待细化（预留的设计空间）：
- 大文件分块加密与断点续传；服务器上的存储键用带密钥的哈希，避免泄露内容哈希。
- 手机按需下载：先同步元信息和缩略图，点开再下载原文件；本地缓存上限与“离线保留”。
- 引用计数与清理：`index.db` 维护文件被哪些卡片引用；回收站里的卡片仍算引用；无引用超过一段时间才清理；永久删除跨设备生效（与 5.4 一致）。
- PDF 高亮与批注作为 CRDT 数据存在卡片或白板文档里（记录文件、页码、区域），不改动 PDF 文件本身。
- 语音速记与转写（结合 0.3 的模型选择）。
- 备份：文件不可变，`assets/` 可做增量备份（硬链接）。
- 视频、超大文件的大小上限与策略。

### 4.7 主题（卡片分组，2026-10）

场景：学习某个主题（例如投资）时，所有相关卡片放在一起。参考 Heptabase：卡片只存一份（卡片库），白板只是引用卡片，同一张卡片可在多块白板上；按主题用两层嵌套白板，白板内用小节分组；标签（带属性的数据库）只用于约 5% 的归档类记录。

**决定**（2026-10-25 修订：起初把主题做成“卡片级标签”，与行内标签同一名字空间；用户指出主题和标签是两个概念，已改为独立对象）
- **主题是独立对象**：有自己的 id 和名字，存于工作区文档；卡片记录它属于哪些主题的 id。改名只改主题本身。卡片可以属于多个主题（不是独占的文件夹）；移出主题或删除主题都不删除卡片。
- **标签保持原样**：正文里的 `#xxx`，有自己的标签页；与主题互不影响。
- **两层嵌套**（如 学习 › 投资），主题页内可分**小节**（基础概念 / 资产配置 / 书单）。白板与主题互相独立（4.3）。
- **子主题**（2026-10-30）：就是有上级的主题，不另设“文件夹”。最多两层，有子主题的主题不能再放到别的主题下；这个限制以后可以放开（数据里的上级字段本来不限层数），反过来放开了就收不回来。上级主题也可以直接放卡片。卡片可以“添加到主题”（保留原有归属），也可以“移动到…”（从当前主题移出），不会自动改动归属。主题可以“移动到…”（另一个顶层主题下，或顶层）、“合并到…”（卡片和子主题并入另一个主题，再删掉自己；给分错、分细的主题用）；删除主题时子主题回到顶层，卡片都在。数量含子主题里的卡片，同一张只算一次。
  - 调研（2026-10-30）：人们找自己的文件更愿意一层层点进去找，好用的结构“浅而宽”（Bergman 等）；整理过早、分得过细会产生没用的“失败的文件夹”（Whittaker）；Johnny.Decimal 只有两级标签，Heptabase 建议白板最多两层、多了先用小节；Evernote 只有一层被长期抱怨；Bear 上级标签可切换“看全部 / 只看自己的”，但允许上下级同时挂会出问题；Capacities、Tana 不做文件夹，Logseq 命名空间争议大。因此：子主题、两层、改起来便宜（移动、合并）、不新增概念；小节以后再做。
- 卡片库的“未归类”视图列出不属于任何主题的卡片，给“每张卡片都有归处”的整理感。

**数据**
- 工作区文档 `ws`（DocKind `workspace`）的根 Map `topics`：主题 id → `{name, parent?, created_at, deleted_at?}`。每个主题的 Map 只由创建它的设备建一次（新 id），字段逐个合并；删除是 `deleted_at` 标记，离线设备回来也能看到。前端启动时打开 `ws` 并一直保持打开（`web/src/docs/topics.ts`）。
- 卡片属于哪些主题：卡片文档 `meta.topics`，**可合并 Map**（主题 id → 加入时间），两台设备同时把卡片放进不同主题都保留（4.5 规则 2）。
- 索引：`idx.card_topics(card_id, topic)`；`topic_cards(id)`、`topic_counts()`。
- 上级出现循环时显示上打断，放回顶层（第二步）。

**分步**
1. ✓（2026-10-25）主题对象（新建 / 改名 / 删除）；**主题在卡片库里展示**（用户要求，不另开主题标签页）：卡片库首页是主题卡片（名称、数量、最新几张卡片、最后编辑时间，末尾“+ 新建主题”），下面是“未归类的卡片”；点主题卡片进入，标题变成“卡片库 › 投资”，⋯ 可重命名、删除；右上角“按主题 / 全部卡片”切换；在首页搜索总是搜全部卡片；把卡片拖到主题卡片上即加入（HTML5 拖放，WebKit 实测可用）；选中卡片后“添加到主题 / 移出此主题”；在某主题下新建的卡片自动加入。卡片标题下的主题行（加入 / 移出，搜索或新建）；侧栏“主题”分区与置顶、标签一样有内容才显示，点击打开卡片库并选中该主题；详情面板列出主题。测试：`web/test/topics.test.ts`（含两台设备各建主题、同时改名与删除、同时把卡片放进不同主题）、`folio-store` 的 `topics_list_their_cards_apart_from_tags`。

## 5. 关键流程

### 5.1 编辑一张卡片

```
用户按键
 → TipTap transaction → loro-prosemirror 写入前端 Loro Doc（本地，零 IPC）
 → DocHub 订阅 doc 的 local update（bytes）
 → persistence.ts 防抖 300ms 合并 → invoke("apply_updates", {doc_id, bytes})
 → Rust: Store::apply_update
     1. 事务内：INSERT doc_updates；INSERT outbox
     2. 内存中的 Rust 侧 Loro Doc import(bytes)
     3. 投递索引任务（后台线程）：提取 title/blocks/links/tags → 更新 index.db
     4. 若标题变了 → emit("card-meta-changed") 让列表/链接显示刷新
 → 同步模块被唤醒，择机上传 outbox
```

- **撤销**：前端每个打开文档一个 `UndoManager`，只撤销本地操作。标题等元数据修改（origin 以 `meta:` 开头）不进编辑器的撤销栈；标题输入框用浏览器自带的撤销。
- **跨文档撤销**（评审补充）：Loro 的撤销管理器是一个文档一个，但一次用户操作可能改多个文档（提炼成卡片改新卡片和日记；把卡片拖进白板改白板；删除卡片改卡片 meta 和白板占位）。应用层维护一个**全局撤销栈**：每次用户操作记为一个“操作组”，记下它在各文档里产生的撤销步骤；撤销 / 重做时整组一起回退或重放。单文档的编辑就是只含一个文档的组。焦点在哪个编辑器，`Mod+Z` 就先撤销那个编辑器里的步骤；不在编辑器里时撤销全局栈的最近一组。
  - **M1a 的实现**（比“记下各文档的撤销步骤”更稳）：编辑器内发起、同时改了别的文档的操作（提炼成卡片），给它在本文档的撤销步骤打标签（Loro 撤销项的元数据，vendor 补丁 3），撤销 / 重做这一步时——无论从哪条路径触发、中间是否撤销过别的输入——按标签对其他文档做相应处理（提炼：撤销时新卡片进回收站，重做时恢复）。打标签前把合并间隔临时设为 0，保证这一步不和之前的输入合并。编辑器外的操作（在卡片库里删卡片）进应用层撤销栈 `AppUndo`。
- **崩溃安全**：未落库窗口 ≤ 300ms；页面关闭/切后台时强制 flush（移动端监听 `visibilitychange`/Tauri 生命周期事件）。

**编辑器集成要点**（来自 M0 预研，详见 ADR 0001；预研实现在 `spike/web/src/editor/extensions.ts`）：

1. **绑定完成前只读**：loro-prosemirror 在 `setTimeout(0)` 之后才把文档载入编辑器，挂载后第一个事件循环内的编辑会与已有内容冲突。编辑器先设为不可编辑，绑定载入完成再打开。
2. **插件顺序**：绑定在 `appendTransaction` 里写 CRDT。所有会修改文档的规范化插件（块 id、结构修复）必须排在它前面（TipTap `priority` 设高），否则一次用户操作会被拆成两次提交、两个撤销步骤。
3. **块 id 规范化覆盖所有事务**：拖动块在绑定里是“删除 + 插入”，撤销或并发编辑后可能出现两个同 id 的块。规范化对本地、远端、撤销产生的事务都生效：首个出现者保留 id，其余改为 `id~n`，各端算出相同结果；远端/撤销引起的修复延后到微任务再提交。
4. **合并后的结构修复**：并发结构编辑可能合并出空列表等不合 schema 的结构，绑定会把它静默丢弃。列表类节点的 content 表达式放宽为允许为空，再由规范化插件清理，把“丢弃”变成“可控修复”。
5. **绑定库 vendor 进仓库并打补丁**：loro-prosemirror 处于 0.x、单一维护方。锁定版本、代码放进仓库，预研的正确性测试（编辑器 3,000 步 + 并发合并 10 万步）加上评审测试（`spike/web/test/review*.test.ts`）作为每次升级的回归测试。必须的补丁：节点的 `attributes` / `children` 改用 mergeable 容器（见 4.5）。已知优化点：远端更新时整篇文档重建（`tr.replace(0, size, …)`），必要时改为按变化节点增量更新。
6. **单卡片块数有上限**：按键耗时随块数增长。M4 在中端手机上实测上限，超长卡片提示拆分。
7. **不用“每台设备都会自动补内容”的插件**：如 TipTap 的 trailingNode（总在文末补一个空段落）、自动插入占位块等。它们在每台设备上各补一次，合并后内容重复。StarterKit 的 `trailingNode` 和 `undoRedo`（撤销由 Loro 负责）都要关掉。预研中已按此配置，未单独测重复现象。

### 5.2a 日记流渲染（评审补充）

每天的日记是一个独立文档，连续日记流往下翻会遇到很多天。规则：
- **虚拟化**：只有视口内及前后少量的日子会被渲染；远处的日子只占位，滚动到附近再加载。
- **编辑器懒挂载**：只为正在编辑的那一天（以及视口内最多约 5 天）挂载 TipTap 编辑器；其余日子显示由 `index.db` 预渲染的只读内容，点击时再挂载编辑器、加载 Loro 文档。与 5.2 白板的“同时活跃编辑器上限”使用同一套机制。
  - M1a 已实现：今天默认挂载，其他日子点击挂载，最多 5 个（最近使用优先），被换下的编辑器保存后从索引读回只读文本；往下滚动按 14 天一页加载。M2 已做虚拟化：离可见区域 1500px 以外的日子只保留上次测得高度的占位，有编辑器的日子始终渲染；每页日记只读一次索引（见 8.6）。只读内容按行画出卡片链接、块引用、#标签和网页链接，样式和点击与编辑器里一致：索引在 `cards.lines` 里为日记存一份带链接的行（`folio_core::body::lines`，JSON；索引版本 10）。
- **按需创建**：打开某一天（包括未来日期）时不立即创建文档，第一次真正写入内容时才创建，避免大量空日记文档。
- **日期以本地日历日期为准**：`journal:YYYY-MM-DD` 取写入时设备所在时区的日期；跨时区旅行时，“今天”跟随当前时区；午夜前开始编辑的块仍属于它所在的那一天的文档，不会自动搬走。

### 5.2 白板渲染（性能核心）

- **LOD 是必须的**（M0 实测，macOS WKWebView）：300 张带 HTML 预览的卡片平移缩放 54–58 fps、卡顿帧 8–18%；只显示标题稳定 60 fps、卡顿帧 < 1%；1000 张预览卡片降到 46–50 fps。只渲染视口内节点（`onlyRenderVisibleElements`）几乎没有收益，可以开但不能依赖。
- **三档 LOD**（按缩放比例和可见卡片数切换）：
  1. 远景：只画标题色块；
  2. 中景：渲染 `index.db` 里的预览 HTML（只读，无编辑器）；
  3. 选中/双击：才为该卡片挂载 TipTap + 加载 Loro 文档。
- 同时活跃的编辑器数量设上限（如 3 个），超出则卸载最久未用的。
- 卡片尺寸变化通过 ResizeObserver 回写 `h`，防抖。

### 5.3 同步协议

**模型**：服务端按 `(workspace_id, doc_id)` 存**只追加**的密文 update 日志，每条有服务端单调递增 `seq`。服务端不理解内容。

```
客户端                                   服务端
  │ ── hello {ws, device, cursor} ───────▶ │
  │ ◀── docs changed since cursor ──────── │   [(doc_id, seq, blob), ...]
  │   解密 → Store::apply_update(origin=remote)
  │ ── push {doc_id, blob(加密 outbox)} ──▶ │
  │ ◀── ack {seq} ───────────────────────── │   删除对应 outbox
  │ ◀══ WebSocket 通知：有新 seq ═════════ │   在线时实时，离线时下次 hello 补齐
```

- **为什么够用**：Loro update 可以重复导入、乱序导入，导入是幂等的；所以服务端只需“存 + 按游标分发”，**不需要 rebase、不需要定序语义**。
- **压缩**（2026-10-28 定稿，本地和服务端都用**完整快照**，不做浅快照）：
  - **为什么不用浅快照**：浅快照（M0 实测：编辑一年的卡片完整快照 2.2 MB → 浅快照 61 KB）裁掉截断点之前的历史后，凡是“前提”不完全在截断点之后的操作都导入不了。原计划“截断到所有设备都已确认的版本”并不够：设备 X 在收到 r 之前做的修改 o，若在 r 已被所有设备确认、截断之后才送达，浅副本拒绝导入（已用 Loro 1.17.1 复现：`ImportUpdatesThatDependsOnOutdatedVersion`），而编辑器里未保存的修改、合盖时没推出去的修改都会落到这种情况。完整快照可以导入任何副本，所以压缩永远不会让修改失去合并的可能。真机上若有卡片因历史太长打开明显变慢，再考虑浅快照，届时设备上报的版本必须是“此后发出的一切都建立在它之后”的版本，并要有从本地备份恢复完整历史的兜底。
  - **本地**：`doc_updates` 达到 200 条或 256 KB 时折叠成完整快照（`crates/folio-store/src/compact.rs`）；首次压缩前做安全备份；每个文档在一个事务里折叠，提交前读回核对内容与版本，否则回滚；有等待依赖的更新时不折叠。每小时在自动备份检查之后运行，每次只锁一个文档。
  - **服务端**：某文档在服务端的更新达到 100 条或 256 KB（`GET heavy`）时，客户端（每小时最多一次，在一次成功同步之后）上传它的加密完整快照，并声明 `covers` = 自己的拉取游标；服务端把快照作为一条新日志（`kind = 'snapshot'`，它的 seq 就是 `snapshot_seq`）追加，并删除该文档 seq ≤ `covers` 的旧条目。快照密封方式和普通更新一样，拉取与导入不需要任何特殊处理；游标落后的设备拿到快照而不是被删掉的那些更新。有等待依赖的更新时不上传。**服务端不保留完整日志**，旧历史靠本地备份（5.4）。
  - **设备确认（`device_acks`）**：每次同步后，设备为“变更计数” `docs.changed` 超过上次报告的文档上报自己的版本向量，按设备绑定后加密，服务端每设备每文档只留最新一条，`GET acks?after=` 按游标取回存进本地 `device_acks`。完整快照方案不依赖它；收敛校验靠它（见下）。
  - **设备列表与移除**：服务端记录每台设备的加密名称和最后一次请求的时间，设置里列出；超过 90 天未同步的标出来，用户可以移除其他设备（`DELETE devices/{id}`）。被移除的设备之后的请求一律 410，需要停止同步再重新加入（新的设备 id）；因为各处都有完整历史，它重新加入时上传的全部历史能直接合并回来。移除不更换口令和密钥（见 5.6 第 5 条）。
  - 模拟器覆盖：随机上传快照、随机移除设备并重新加入、最后加入一台全新设备，全部收敛。
- **收敛校验**（学 Logseq ADR 0006，2026-10-30 实现，`crates/folio-sync/src/client.rs`）：用上面的版本报告，不另传哈希。
  - **报告轮次**：设备每次报告结束时附上一轮的结尾 `Round { through, number, started }`：`through` 是拉取游标，表示本轮及之前报告的版本在该游标时都成立；`number` 是轮次编号；`started` 是设备开始编号的时间。outbox 里还有待推送更新的文档不进本轮（它的版本还不在服务端），留到下一轮。服务端在设备列表里记下每台设备的 `acked_through`、`acked_round`、`acked_started`。
  - **比较**：每 10 分钟一次，先取设备列表再取报告（设备先发报告后发游标，所以游标担保的报告都能取到）。对 `acked_through` 不小于本机报告游标的每台设备，若它报告的版本不包含本机报告的版本，本机把 `updates_since(它的版本)` 放进 outbox 补发；同一设备、同一文档、同一版本只补发一次。补发了东西时记一条警告，并很快再同步一次。
  - **服务端回到旧副本**（从备份恢复）：副本之后存下的更新和报告丢了；而且如果 seq 被重新使用，设备会跳过落在自己游标之下的新条目。所以服务端每次启动把更新日志和报告日志的 seq 起点抬到当前时间（微秒），退回后新给的 seq 一定大于退回前给过的（除非每秒给出超过一百万个）。丢掉的部分要靠设备发现，三处能发现：拉取时 head 小于本机游标；报告时服务端拒收这一轮（服务端只接受第一轮、紧接上一轮的一轮，或重复上一轮——回复丢了时；否则不记下轮次，缺口一直留着，回复丢了重发也照样看得到）；校验时设备列表里本机的轮次比本机记录的少、开始编号的时间对不上，或服务端存着的本机报告（设备列表带有每台设备的报告条数）比本机发出去的少——最后这条管的是“回复丢了，同一个轮次号又发了别的报告”之后再退回的情况，轮次号看不出来。发现后本机按新设备重来（清游标与报告，全部历史放进 outbox，重新编号轮次）。其他设备看到它的 `started` 变了，就从头重新取一遍报告，免得漏掉落在已越过的 seq 上的报告。
  - 实测：把校验关掉，模拟器有的种子永远不收敛（某台设备缺内容而无人补发），打开后全部收敛。
- **附件**：按 sha256 内容寻址，分块加密后经单独的接口上传，服务器存成文件；卡片里只存哈希（存储见 4.6，同步设计见 `design/attachments.md` §5，2026-10-28 已实现，接口为 `POST blobs/have`、`PUT/GET blobs/{id}/{n}`、`POST blobs/{id}/done`、`PUT blobs/refs`）。
- **E2EE**：工作区主密钥用用户口令（Argon2id）派生的 KEK 包裹后存服务端；新设备输入口令解开。所有 blob 用 XChaCha20-Poly1305 加密，`doc_id` 也可做 HMAC 混淆。
- **恢复码（2026-10-31）**：设置里可生成恢复码（160 位随机，Crockford base32，8 组 × 4 字符，只显示一次）；主密钥再用它包裹一份存服务端（`workspaces.recovery_key`，`PUT/GET /v1/w/{ws}/key/recovery`），服务端看不到恢复码。忘了口令时，新设备凭同步码 + 恢复码解开主密钥并设新口令（`PUT key/passphrase` 替换口令那一份）；已在同步的设备有主密钥，不受影响，也不重新加密任何内容。已有设备也可直接更改口令。重新生成会让旧恢复码失效。纯新增：旧服务器返回 404 时提示升级服务器，旧数据不动。
- **第一版实现（M3，2026-10）**：`crates/folio-sync`（协议、加密、服务端存储 `relay`、客户端引擎 `client`、HTTP/WebSocket 传输）+ `crates/folio-server`（axum）。与上面草图的差别：日志按**工作区**一条，`seq` 与游标都是工作区级的（一次拉取覆盖所有文档）；`doc_id` 用 HMAC 混淆成标签，文档种类和真实 id 封在密文信封里，服务端只看到“某工作区、某标签、某设备的一段密文”。接口：`PUT/GET /v1/w/{ws}/key`（包裹后的主密钥）、`POST push`、`GET pull?after=`、`GET live`（WebSocket，只通知新的 head）、`PUT device`（加密的设备名）、`GET devices`、`POST/GET acks`（加密的版本报告）；所有请求带服务器令牌（启动时的 `FOLIO_SERVER_TOKEN`）和设备 id。新设备凭“同步码”（服务器地址 + 令牌 + 工作区 id）加口令加入；口令不在同步码里。设备开启同步时把每个文档的完整历史放进 outbox 一次，之前写入的内容（迁移、恢复、导入）不会漏传。工作区主密钥存系统钥匙串（2026-10-31，见 5.6 第 4 项）。附件已于 2026-10-28 加入，收敛校验、跨设备永久删除已于 2026-10-30 加入。
- **无服务器模式（可选，后期）**：同样的协议也可以落到 WebDAV / iCloud Drive / S3：每台设备只写自己的 `ops-<device>/` 目录（单写者），其他设备读取 → 天然无冲突（tine BACKLOG 中提到的思路，在 CRDT 下变得简单）。

**部署（2026-10-26）**：`scripts/install-server.sh`，在装有 systemd 的 Linux 上以 root 运行，参数只要域名。下载 Release 里的静态二进制（`folio-server-{x86_64,aarch64}-linux`，musl，附 sha256 校验）。全部文件在 `/opt/folio-sync`：`bin/`（程序、管理命令 `folio-sync`、安装脚本副本）、`etc/folio-sync.env`（令牌和设置，root 所有、0640；令牌只生成一次，重跑沿用）、`data/`（数据库）、`logs/folio-sync.log`（systemd 240+ 写文件，logrotate 每天轮转、保留 14 天；更老的 systemd 留在 journal）、`VERSION`。系统用户与 systemd 服务都叫 `folio-sync`，只监听 `127.0.0.1:8787`，带沙箱选项（只能写 `data/` 和 `logs/`）。管理命令软链到 `/usr/bin/folio-sync`（有的系统如 OpenCloudOS 的 sudo 搜索路径不含 `/usr/local/bin`）：`status`（服务状态 + 健康检查）、`start` / `stop` / `restart`、`logs [-f]`、`info`（地址、令牌、版本、路径）、`upgrade [--version]`（取最新安装脚本重跑，离线时用本地副本）、`uninstall [--purge]`。HTTPS 交给 Caddy（参照自建 Logseq 同步的做法，不依赖系统包管理器）：机器上没有 Caddy 时，询问后下载 Caddy 官方发布的二进制（版本固定为 2.11.7，SHA-512 写在脚本里校验），装在 `/opt/folio-sync/bin/caddy`，配置和证书在 `/opt/folio-sync/caddy/`，以系统用户 `folio-caddy` 运行独立服务 `folio-sync-caddy`（只开放绑定低端口的能力），日志写 `logs/caddy.log`；装之前先检查 80 和 HTTPS 端口是否被别的程序占用并说出是谁，有冲突就在改动任何东西之前停下；可换 HTTPS 端口（证书仍走 80，并关闭 TLS-ALPN 验证），与自建 Logseq 同步一致：在终端里直接运行时按步骤询问域名、公网 HTTPS 端口（默认 443，换成别的端口可以避开大部分扫描）和本机端口，回车用括号里的值；再列出安装计划（地址、端口、HTTPS 怎么配置、安装位置、安全组要放行的端口），同意后才动手。重跑和 `folio-sync upgrade` 沿用上次的端口；`--domain`、`--https-port`、`--port`、`--yes` 用于无人值守。机器上已经有系统的 Caddy（用 `/etc/caddy/Caddyfile` 管理）时，询问后追加站点（先备份、`caddy validate` 通过才写入、保留文件的属主和权限、用标记行包住，重跑时整块替换，改域名会再问一次）；Caddyfile 里已有同名站点就不动，只提示；Caddy 不是用 `/etc/caddy/Caddyfile` 管理的（如 Docker）就打印配置片段。还会检查域名是否解析到本机、端口是否被占用、ufw / firewalld 是否需要放行 80/443，最后等 `https://域名/health` 可访问并打印服务器地址和令牌。`folio-sync uninstall`（或 `--uninstall`）移除服务与程序，数据、令牌、日志留在 `/opt/folio-sync`；`--purge` 整个目录和用户一并删除。客户端实时通道支持 `wss://`（tungstenite 开启 rustls）；服务端收到 SIGTERM 会正常退出。CI 的 `Server install` 在全新的 Ubuntu 上跑全流程（装 Caddy、目录与权限、管理命令的启停与日志、重跑保留令牌、与其他站点共用 Caddyfile、卸载、彻底删除）。

### 5.4 删除与恢复

- 卡片/白板：`meta.deleted_at = now`（这本身是 CRDT 字段，可同步），回收站视图列出。
- **永久删除（清空回收站）必须跨设备生效**（评审补充）：只删本机数据的话，其他设备和服务端的副本下次同步又会把文档带回来。做法：在 workspace 文档的 `purged`（mergeable Map）里写入 `doc_id → 删除时间`；所有设备看到后删除本地文档与索引，并拒绝再导入该 `doc_id` 的更新；服务端收到客户端的清除请求后删除对应的加密日志与快照。
  - **已实现（2026-10-30）**：回收站右上角“清空回收站”（先确认，说明所有同步设备上都会删除、无法恢复）；在回收站里超过 **30 天**的卡片每小时检查一次自动永久删除（在当天的自动备份之后，按卡片自己的 `deleted_at`，所以每台设备算出的结果一致）。新版之前就在回收站里的卡片是按“随时可以恢复”放进去的，30 天从这台设备第一次运行新版时算起（本机设置 `trash.cleanupSince`），升级当天不会删除任何东西。
  - 本机（`Store::purge_cards`、`apply_purges`）：写进 `ws` 文档的 `purged` 后，删掉 `docs`、`doc_updates`、`outbox`、`device_acks` 里这个文档的行和全部索引行，记进 `purged` 表；之后这个 id 的任何更新（别的设备发来的、编辑器里还没存的）一律丢弃。`ws` 文档每次更新（本机或同步来的）和每次打开资料库时都对照一遍，所以别的设备、以及旧版本升级上来的资料库都会跟着删除。附件随索引行消失变成“无人使用”，按 attachments.md §6 的规则清理。本地备份里还有，随备份轮换消失。
  - 服务端：`POST /v1/w/{ws}/purge`（文档标签，一次最多 1000 个）删除这些文档的全部更新和快照，并记下标签，之后还推上来的（没听说删除的设备）直接丢掉。每台设备都会告诉服务端一次（不依赖删除的那台还在）；拉取时如果还收到已删除文档的更新（服务端退回了旧副本），再告诉一次。版本报告（只有版本向量，没有内容）保留，设备的报告条数校验才不会误判。旧版服务端不认识这个请求时只记一条警告，各设备照样删除。
  - **日记不永久删除**：日记的 id 就是日期，永久删除后那一天就再也写不了；清空回收站时日记留在回收站里（现在界面上也没有把日记移进回收站的入口）。
  - 冲突时删除优先：一台设备离线时把卡片从回收站恢复并修改，另一台已经永久删除，同步后照样删除。从更早的备份恢复整个资料库，可以撤销还没同步出去的永久删除。
  - 模拟器覆盖：随机移进回收站、恢复、清空回收站、按时间自动清理，结束时断言被删的卡片在每台设备上都不存在、服务端没有它的任何更新。
- **备份与恢复**：每日自动 `VACUUM INTO` / SQLite backup API 生成本地备份，保留最近 N 份。恢复**不能**直接替换数据库（评审补充）：备份里的同步游标也是旧的，恢复后同步会把新内容全部拉回来，等于没恢复；而如果服务端也只有旧内容，被替换掉的新修改就丢了。正确做法分两种：
  - **恢复某张卡片的旧版本**：用 Loro 切到历史版本，算出与当前版本的差异，作为一次**新的编辑**写回（可同步、可撤销）。历史版本只能追溯到压缩点，所以本地备份同时保存完整快照，供更早的版本使用。
  - **整库灾难恢复**（本机数据损坏）：用备份重建本地库后，与服务端做一次完整同步；本地备份里有、服务端没有的修改照常上传，不会丢。恢复时删掉副本里存的 Loro peer id（`peer.rust`、`peer.frontend`、`peer.api`），之后的编辑用新的 peer id：沿用旧的会和备份之后已经发出去的操作撞号，Loro 拒绝导入（“Every op id should be unique”），这台设备的同步就停了（2026-10-30 模拟器发现）。版本报告（`device_acks` 和 `sync.acks.*`）也一并清掉：备份里的报告比现在的内容新，别的设备会以为这台已经有了，不再补发。
  - 恢复前先做安全备份（学 tine ADR 0007）。

### 5.5 导入 / 导出

- **Logseq Markdown 导入**：页面 → 卡片；顶层块 → 列表块；`[[x]]` → cardLink（不存在则建空卡片）；`((uuid))` → blockRef（`id::` 映射为 bid）；`tags::`/`#tag` → 标签；journals → 日记。只做常见语法的子集，其余原样保留为文本。
- **Markdown 镜像/导出**：从 Loro 文档渲染 md 到 `mirror/` 目录，永不回读（学 Logseq ADR 0016）。
- **Heptabase 导出导入**（后期）：其导出是 md + 白板 JSON，可映射到 card/board。

### 5.6 数据安全与隐私（产品化前必须完成）

做成产品后，用户最担心的两件事是**数据丢失**和**笔记被别人读到**。端到端加密和本地优先已经回答了大部分，下面这些是从“自己用”到“给别人用”之间必须补上的缺口。**在官方托管同步或公开发布之前全部完成**；新功能涉及数据流向时，先对照这一节。

**现状（M3 第一版）**：内容和文档 id 在本机加密，服务器只存密文和不透明标签；服务器会看到的元数据：同步时间、每条更新的大小、设备 id、工作区 id、同一文档的更新数。不用 HTTPS 时内容仍是加密的，但令牌、同步码、包裹后的主密钥会明文传输（后者可被离线猜口令）。

| # | 缺口 | 做法 | 为什么重要 |
|---|---|---|---|
| 1 | 传输 | 官方托管只接受 HTTPS；自托管使用 http 时，在同步设置里明显提示（局域网测试除外） | 令牌与包裹后的主密钥不能明文传 |
| 2 | **忘记口令** ✅ 2026-10-31 | 开启同步时生成**恢复码**（类似 1Password 的 Secret Key / Bitwarden 恢复码），要求用户保存并确认；口令可用恢复码重置 | 端到端加密下官方也无法找回；用户会把“进不去”当成“数据丢了”，是最大的口碑风险 |
| 3 | 口令强度 | 设置口令时显示强度，拒绝常见弱口令；Argon2id 参数随硬件调高 | 服务器或截获者拿到包裹后的密钥可离线猜口令 |
| 4 | **本机密钥** ✅ 2026-10-31（静态加密未做） | 工作区主密钥存系统钥匙串（macOS/iOS Keychain、Windows 凭据管理器、Linux Secret Service、Android Keystore），不存本机设置；本地数据库静态加密作为选项（参考 Notesnook 的 sqlite-multiple-ciphers） | 资料库（及其备份、被同步盘或复制带走的副本）不再含主密钥 |
| 5 | 账号与设备 | 账号体系；每台设备单独的凭证，替代共用的服务器令牌；设备列表可单独移除；移除后轮换主密钥（重新加密，新密钥只发给留下的设备） | 丢了手机要能只撤销那一台；同步码泄露要能补救 |
| 6 | 真正的删除 | 跨设备永久删除（5.4）同时删除服务器上的对应密文（2026-10-30 已做：清空回收站、回收站 30 天自动清理）；注销账号清空服务器上的全部数据；写明保留期限 | 用户期待，也是法规要求（GDPR、《个人信息保护法》的删除权） |
| 7 | 服务器数据量 | 压缩（已做）：服务器只保留每个文档最新的加密完整快照 + 之后的更新，旧条目在上传快照时删除（5.3）；可选“信箱模式”（所有设备收到后即删，代价是没有异地副本、新设备要从老设备取数据） | 删掉的旧内容不应无限期留在服务器上 |
| 8 | 元数据最少化 | 服务器只记录运行必需的信息，日志不含文档标签，IP 不长期保存；更新大小可做填充（按档位补齐） | 安全说明里要能如实列出服务器知道什么 |
| 9 | AI 与加密 | 服务器端不做任何需要读内容的 AI；AI 只在本机运行，或由用户明确选择把指定内容发给模型服务商，每次标明发往哪里；默认不发送 | “端到端加密”和“AI 原生”同时宣传时，这一点讲不清会失去信任（0.3） |
| 10 | 可验证 | 一页通俗的安全说明（服务器能看到 / 看不到什么，含元数据）；公开协议与客户端加密代码；用户规模上来后做第三方安全审计；保留自托管 | 让用户能验证，而不只是相信 |
| 11 | 合规（中国） | 国内托管涉及 ICP 备案、数据境内存储、《个人信息保护法》；上线前请专业人士确认 | 全球化产品，各地区要求不同 |

**第 4 项的做法**（2026-10-31，`src-tauri/src/secret.rs`）：
- macOS、iOS 存 Keychain，Windows 存凭据管理器，Linux 存 Secret Service；服务名 `Folio`，账户 `sync key {工作区}/{设备}`，同一台电脑上的多个资料库互不相干。Android 用 Android Keystore 里不可导出的 AES 密钥以 AES-GCM 加密主密钥，密文留在本机设置（`folio-apk` 插件的 `seal` / `open`）。
- 同步设置里 `keyIn` 记录存在哪里，`key` 留成空字段（旧版本仍能读出设置）。
- **升级**：启动时把设置里的明文密钥写入钥匙串，读回一致后才清掉明文，只做一次。没有钥匙串（如没有 Secret Service 的 Linux）时照旧存在设置里，同步不受影响。
- **读不到密钥**（资料库复制或恢复到另一台设备、Android 从云备份恢复）：同步页提示，停止同步后用同步码 + 口令重新加入，笔记不受影响。停止同步时删除钥匙串里的这一项。
- 页面读写本机设置的命令不再能碰同步设置（`sync`、`sync.*`），以前页面脚本能读到令牌和密钥。
- **仍有的缺口**：升级前的自动备份里还有明文密钥，随备份轮换消失；降级回 0.1.9 及更早版本后同步会停，需重新加入。
- 验证：桌面两个旧资料库升级后照常同步、删掉钥匙串项后提示；Pixel 5 升级、新加入、重启后照常同步，密文损坏时提示且能重新加入；iOS 模拟器升级与重启后照常同步。macOS 上重新编译（签名变化）后读取钥匙串不弹密码框。

**端到端加密的代价**（设计相关功能时考虑）：网页版需在浏览器内解密；分享与多人协作需要交换密钥；服务器端搜索和服务器端 AI 不可行。

### 5.7 资料库位置（2026-10-25）

资料库就是一个文件夹（`store.db`、`index.db`、`backups/`）。默认在应用数据目录（macOS：`~/Library/Application Support/dev.folio.app/data`），用户可以在“设置 → 备份与导出 → 资料库位置”改。
- **记在哪**：选了别的位置时，应用数据目录里写一个 `library.json`（`{"path": …}`，写临时文件再改名）；移回默认位置就删掉它。资料库自己的设置都在 `store.db` 里，跟着资料库走。环境变量 `FOLIO_DATA_DIR` 优先，此时界面里不能改。
- **启动**：`library.json` 指向的文件夹里有 `store.db` 才打开它；不在（外接硬盘没接）就打开默认资料库、保留这个选择、记错误日志并提示用户，**绝不在原处新建空库**（否则看起来像笔记丢了）。
- **移动到…**：选一个文件夹，空的就直接用，不空就在里面建 `Folio`（已存在且不空、已有资料库、在当前资料库里面、就是当前位置，都拒绝并说明）。过程：停同步 → 关闭资料库 → 复制到目标旁的临时文件夹 → **逐个文件比对字节** → 改名到目标 → 写 `library.json` → 原文件夹改名为 `<名字>.moved-<时间>` **保留不删**（写 `library.json` 失败就把原文件夹改回去）→ 打开新位置 → 重启同步，前端重新加载。任何一步失败：原资料库不动，删掉半成品，重新打开原资料库。
- **打开其他资料库…**：选的文件夹是资料库就打开，空文件夹就新建，有别的东西就拒绝。当前资料库原样留着，随时可以再打开。还有“移回默认位置”“在访达中显示”。
- **网盘文件夹**（iCloud Drive、`~/Library/CloudStorage`、Dropbox、OneDrive、Google Drive）：确认时和设置里都警告——网盘可能在写入中途复制 SQLite 文件导致损坏；两台电脑打开同一个资料库还会共用同一个 Loro peer id（存在 `store.db` 里），破坏合并（§4.5 规则 3）。多设备用 Folio 自己的同步（§5.3）。
- 不重启进程：和恢复备份一样在原地换掉打开的 Store（`tauri dev` 下重启会结束开发会话）。
- 测试：`src-tauri/src/library.rs`（指针、文件夹判断、目标选择、移动保留原件、失败不留半成品）、`lib.rs`（移动后卡片还在且记住位置、移回默认、打开其他 / 新建 / 拒绝、失败的移动停在原处）；用临时 HOME 启动应用验证三种启动情况；WebKit 验证设置界面的各种确认文字。

## 6. 插件系统

### 6.1 设计原则

1. **能力封闭、宿主代办**：插件拿不到 DOM、Tauri `invoke`、文件系统、网络套接字；只能调用宿主提供的**语义操作**（如“给卡片加标签”“在光标处插入块”），由宿主检查权限后执行。这同时满足苹果审核 4.7.2，所以 iOS 也能开放插件。
2. **与用户编辑同一条写入路径**：插件的写操作落到 Loro 文档，走 `persistence` → `Store::apply_update`，可撤销、可同步、可审计（日志标注 `origin=plugin:<id>`）。
3. **API 版本化，内部可自由重构**：插件只依赖 `@folio/plugin-sdk` 定义的公开 API（semver），不接触 Loro 结构和 SQLite 表。Logseq 迁 DB 版时插件大面积失效，就是因为插件直接依赖了内部数据模型。
4. **卸载插件不损坏数据**：插件写进卡片的内容（自定义块、属性）在插件缺席时必须仍可读——以“原始数据 + 回退渲染”展示。
5. **自家功能先用插件 API 实现一部分**（如 Markdown 导出、模板、日历视图），保证 API 真的够用。

### 6.2 三种扩展包

| 类型 | 内容 | 运行方式 | 风险 |
|---|---|---|---|
| **主题** | 宿主白名单内的设计 token（颜色、字体、圆角）+ 可选设置 | 纯数据，无代码 | 极低 |
| **插件** | 逻辑代码（TS 编译成单个 JS bundle）+ manifest | QuickJS-wasm 沙箱，每个插件一个 Worker | 受能力约束 |
| **插件视图**（插件的一部分，需单独声明能力） | 自定义渲染：特殊块（图表、Mermaid、看板）、白板上的自定义元素、侧栏面板 | `sandbox="allow-scripts"` 的 iframe，`srcdoc` 加载，严格 CSP 禁网络，只能通过 postMessage 与宿主通信 | 中，标记为实验性 |

> 大多数插件只需要第二种：注册命令、斜杠菜单、处理事件、读写卡片，再用**声明式 UI** 显示结果。声明式 UI 是插件返回的 JSON 组件树（列表、表单、表格、Markdown、按钮、图表），由宿主用自己的组件渲染，风格统一、移动端也能用。只有确实需要自定义绘制时才用 iframe 视图。

### 6.3 运行时架构

```
主线程（宿主 UI）
  PluginHost
   ├─ 读取 manifest，校验能力、平台、API 版本
   ├─ 为每个插件起一个 Worker ── 内含 QuickJS-wasm ── 插件 bundle
   │      ▲  版本化 JSON-RPC（请求/事件/返回值，全部是纯数据）
   │      ▼
   ├─ CapabilityGate：每次调用检查权限 → 调用内部 API（DocHub / query client）
   ├─ 资源限制：单次调用超时、内存上限（wasm memory max）、超限即终止 Worker
   └─ 渲染插件贡献的 UI：命令、斜杠菜单项、声明式面板、iframe 视图
```

- **为什么选 QuickJS-wasm 而不是直接用 Worker**：普通 Worker 里仍有 `fetch`、`importScripts`、IndexedDB 等环境 API，很难完全封住；QuickJS 是一个“空白”的 JS 引擎，里面除了宿主注入的东西什么都没有（Figma 的插件就是这么做的）。代价是比 V8/JSC 慢，但插件多是胶水逻辑，够用；需要重计算的插件可以额外附带 Wasm 模块。
- **为什么不只用 Wasm（tine 的做法）**：Wasm-only 的门槛让大多数社区作者望而却步；TS 插件 + 完整类型 + AI 指南，才能让生态起来。

### 6.5 能力与 API（v1 草案）

| 命名空间 | 能力 | 说明 |
|---|---|---|
| `commands` | `commands.register` | 注册命令（命令面板、快捷键） |
| `editor` | `editor.slash`、`editor.insert`、`editor.selection.read` | 斜杠菜单、在光标处插入块、读取选区 |
| `cards` | `cards.read`、`cards.write.meta`、`cards.write.body`、`cards.create` | 读取卡片；修改标题/标签/属性；修改正文；新建卡片 |
| `boards` | `boards.read`、`boards.write` | 读白板、增删移动白板元素 |
| `query` | `query.search`、`query.backlinks`、`query.tag` | 走 `index.db` 的只读查询（类型化查询构造器，不开放原始 SQL） |
| `events` | 随对应读权限自动可用 | `card.changed`、`board.changed`、`journal.opened`、`app.ready` |
| `ui` | `ui.notify`、`ui.panel`、`ui.modal`、`ui.iframe` | 通知；声明式面板/对话框；沙箱 iframe 视图 |
| `blocks` | `blocks.customType` | 注册自定义块类型（数据存在节点属性里，插件缺席时显示原始数据） |
| `storage` | `storage.local`、`storage.sync` | 本设备存储；随工作区同步的插件数据（存在 workspace 文档的 `plugins.<id>` 下，用 mergeable Map，见 4.5） |
| `net` | `net.fetch:<域名>` | 由宿主代发请求，只允许声明过的域名 |
| `files` | `files.pick`、`files.save` | 必须由用户在系统对话框里选择；用于导入/导出插件（Notion、Obsidian、Readwise 等） |

### 6.6 分发与信任

- **注册表**：一个公开 GitHub 仓库，存插件索引 JSON（学 Obsidian community-plugins）。每个版本记录：不可变 sha256 摘要、源码地址、许可证、能力与平台声明、自动审计结果。
- **审核**：CI 自动检查 manifest、能力申请是否与代码相符、包大小；低风险自动上架，高风险能力进入人工复核。
- **吊销**：签名的吊销列表，客户端启动时拉取，可远程禁用已知恶意版本。
- **应用内**：设置里浏览、安装、启用、配置、卸载；iOS 上按苹果要求以“设置中的插件目录”形式呈现，不做“商店”。
- **开发模式**：从本地文件夹加载插件，文件变化自动重载；提供 `folio-plugin` 脚手架和 Web 模式下的调试宿主。

### 6.7 开源许可建议

- 如果主程序选 AGPL-3.0：把 `@folio/plugin-sdk` 单独以 **MIT** 发布，并在主程序许可证里加**插件例外条款**，声明通过公开插件 API 交互的插件不视为衍生作品，社区作者可以自选许可证。
- 如果希望商业友好：主程序直接用 MPL-2.0 或 Apache-2.0，问题更简单。

### 7.1 IPC 命令（初版，约 20 个）

| 类别 | 命令 |
|---|---|
| 文档 | `open_doc(doc_id) -> bytes(snapshot+updates)`、`apply_updates(doc_id, bytes)`、`create_card(kind, title?)`、`create_board(title)`、`delete_doc` / `restore_doc` |
| 查询 | `list_cards(filter, sort, page)`、`search(q, limit)`、`backlinks(card_id)`、`unlinked_refs(card_id)`、`card_boards(card_id)`、`resolve_titles(ids)`、`tag_table(tag_id, query)`、`journal_range(from, to)` |
| 附件 | `put_asset(bytes) -> sha256`、`asset_url(sha256)`（自定义协议 `folio-asset://`） |
| 同步 | `sync_status()`、`sync_now()`、`sync_login(...)`、`set_passphrase(...)` |
| 维护 | `snapshot_now()`、`list_snapshots()`、`restore_card_version(card_id, version)`（作为新编辑写回，见 5.4）、`disaster_restore(backup_id)`（本机数据损坏时重建本地库，之后与服务端完整同步）、`rebuild_index()`、`import_logseq(dir)`、`export_markdown(dir)`、`export_diagnostics()`（日志与环境信息，不含笔记内容） |

### 7.2 发布、签名与商店（评审补充）

不签名的应用会被系统警告或拦截（tine 的 README 就在教用户绕过 macOS 的“身份不明的开发者”提示）。各平台要求与成本：

| 平台 | 要求 | 成本 / 限制 |
|---|---|---|
| macOS | 开发者证书签名 + 苹果公证（notarization），否则 Gatekeeper 警告 | 苹果开发者计划约 99 美元 / 年（与 iOS 共用） |
| iOS | 必须经 App Store 或 TestFlight 分发 | 同上；App Store 与 TestFlight 公开测试都需审核（通常一到数天）；**TestFlight 内部测试（开发者团队成员）无需审核**，适合自用快速迭代 |
| Windows | 代码签名证书，否则 SmartScreen 拦截 | 商业证书按年付费；或使用微软的云签名服务；也可先不签名，靠用户手动放行（体验差） |
| Android | 应用签名密钥；上架 Google Play 需开发者账号 | Play 一次性 25 美元；也可直接分发 APK |
| Linux | 无强制签名 | AppImage / deb / rpm |
| 自动更新 | `tauri-plugin-updater` 要求更新包签名 | 自管一对更新签名密钥，私钥只放在 CI 的密钥库里，丢失则无法再推送更新 |

这部分费用与“低成本”原则有冲突但无法避免；建议 M0 先用自签名 / 不签名在自己的设备上跑通，M2 日常可用前办好苹果开发者账号（macOS 公证 + iOS TestFlight），Windows 签名在公开发布前解决。

### 7.3 构建与自动更新（2026-10-25）

- **仓库**：`github.com/linlih/folio`（公开）。`CI` 每次推送跑全部测试；`Build apps` 手动运行或推送 `v*` 标签时构建 macOS（通用 `.dmg`）、Windows（`.msi` / `.exe`）、Linux（`.deb` / `.rpm` / `.AppImage`）、安卓 APK（arm64），iOS 暂时只检查能否编译。
- **发布**：`./scripts/release.sh 0.2.0 -m "更新说明" --push`——改 `tauri.conf.json`、`Cargo.toml`、`web/package.json` 和两个锁文件里的版本号，提交，打带说明的标签并推送。标签触发构建：先建 Release（说明取自标签），各平台构建把安装包和更新包（含签名）加进去；三个桌面构建都成功后，由一个单独的任务（`scripts/latest-json.py`）按签名文件写一次 `latest.json`，缺任何平台就不写（v0.1.10 时三个构建同时改它，丢了 Mac 的条目）；安卓 APK 以固定文件名 `folio-android-arm64.apk` 上传。Release 直接发布（不是草稿），`releases/latest/download/…` 才能指向它。
- **桌面自动更新**：`tauri-plugin-updater` 读 `releases/latest/download/latest.json`，下载后用 `tauri.conf.json` 里的公钥校验签名再安装，装完 `tauri-plugin-process` 重启。签名私钥在仓库 Secrets（`TAURI_SIGNING_PRIVATE_KEY` 及密码），本机备份在 `~/.folio-signing/`；**私钥丢失则已安装的应用再也无法自动更新**。Linux 只有 AppImage 能自更新。
- **安卓**：更新插件不支持手机。应用通过 Rust 命令读同一个 `latest.json`（网页跨域读不了），有新版本就提示；“下载并安装”在应用内下载该版本的 APK（`releases/download/v<版本>/folio-android-arm64.apk`，显示进度，长度不符则作废），存到缓存的 `updates/`，再由本地插件 `crates/folio-apk`（Kotlin，经 FileProvider）打开系统安装界面。第一次需要用户允许 Folio 安装应用：插件改为打开系统的授权页，回到应用后自动继续安装。系统只接受与已装应用同一签名的 APK（都用仓库 Secrets 里同一把密钥签名），所以下错或被篡改的文件装不上；下载失败时可改用浏览器下载。旧的安装包在下次启动时清掉。**iOS** 只能经 App Store / TestFlight 更新。
- **界面**：启动 8 秒后、之后每小时看一次是否已过一天，满一天就静默检查；有新版本时右下角卡片显示版本和说明：立即更新（下载进度、重启前先保存）/ 稍后 / 跳过此版本（静默检查不再提示该版本，手动检查仍会提示）。设置 → 关于：检查更新、自动检查开关。失败的静默检查（离线）不提示。

## 8. 里程碑（单人 + AI 辅助的粗估）

顺序原则：**先做到自己能每天用它记笔记（M2），边用边修**，再做同步、移动端，然后才是白板和插件（见 0.1 产品原则第 2 条）。

### 8.4 卡片库（参考 Heptabase）

Heptabase 闭源，只能参考公开资料（官方 wiki、更新日志、用户教程）：卡片都存在卡片库里，白板只是引用（同一张卡片可在多个白板上）；卡片信息里能看到它在哪些白板上、有哪些标签和反链；卡片库支持排序（v1.25）和按属性、日期、标签、白板过滤（v1.110 起，包括“不在任何白板上”），有“删除空白卡片”；卡片库可在右侧栏打开，点卡片在侧栏参考，拖到白板上。资料：wiki.heptabase.com 的 user-interface-logic、fundamental-elements、changelog、roadmap。

Folio 现在的卡片库：
- 两种视图：列表（标题、两行摘要、日期）与卡片网格（卡片预览，同 Heptabase 的 grid view），可切换并记在本机。
- 工具栏：搜索（标题和摘要，多个词须全部命中）、“编辑于”过滤（今天 / 最近 7 天 / 最近 30 天）、排序（最后编辑 / 创建时间 / 标题，数字按数值排、无标题排最后）；排序与过滤记在本机设置里。
- 每行：标题、两行摘要、右侧最后编辑时间（今天只显示时刻）和创建日期。
- 多选：悬停出现复选框，`Shift` 连选；已选时出现操作条，可全选、一起移到回收站（一次撤销全部恢复）。
- “清理空白卡片”：没有标题也没有内容的卡片一次移到回收站。

跟着后续里程碑补上：按白板过滤（含“不在任何白板上”）与“所在白板”列（M5 白板）；按标签和属性过滤、标签列（M6 标签数据库）；在右侧栏打开卡片库、拖卡片到白板（M5）；全文搜索（M2 FTS，现在只搜摘要的前 160 字）。

### 8.6 M2 进度（第一批：反链、搜索、块引用、快速记录）

已完成（有自动测试的标 ✓）：
- **索引**（index.db 版本 3，旧索引打开时重建）：每张卡片保存时提取块、卡片链接、块引用（Rust `folio-core/src/index.rs`，前端内存后端用同规则的 `web/src/docs/index.ts`）✓。块 = 大纲项（首行加其中的其他段落）或列表外的顶层文字块；行内的卡片链接、块引用、换行、行内公式留在所在行内。表：`idx.links(from_card, from_bid, to_card)`、`idx.refs(from_card, from_bid, to_bid)`、`idx.fts`（FTS5 trigram，标题一行 bid 为空）。与 4.4 的初稿不同，链接和块引用分两张表，查询更直接。
- **反链**：卡片底部列出链接到本卡片的块，以及引用本卡片中块的块（标“块引用”），按来源卡片分组，点击跳到来源块并高亮 ✓。**未链接引用**：正文提到标题但没有链接的块，默认折叠 ✓。回收站里的卡片不计入。

- **块引用**：`((` 搜索块并插入；在块里不选文字按 Mod+C 复制该块的 `((id))`，粘贴回来变成块引用 ✓；显示被引块的当前文字，点击跳过去。卡片链接同样显示卡片当前标题（改名后自动更新）。
- **快速记录**：应用内 Cmd+E，桌面全局 Cmd+Shift+Space（唤起主窗口）；每行一个块，`[ ] ` 开头的行成为任务，Mod+Enter 写入今天的日记 ✓。
- 定位高亮用编辑器装饰实现（`web/src/editor/reveal.ts`），不会被打开标签页后的重绘冲掉。

### 8.1 M0 技术预研（已完成）

> **结果**：选定 **Loro**，数据与理由见 [ADR 0001](adr/0001-crdt-choice.md)，预研代码与原始数据在 `spike/`。两库都通过了否决项（Yjs 需一行补丁）；决定性差异是第 4 项：编辑一年的卡片 Loro 压缩后 61 KB，Yjs 2.3 MB 且无法压缩。白板验证的结论见 5.2 节。未覆盖：中英文输入法（移到 M1）、移动端真机（移到 M4）、Chromium 系 WebView 的白板帧率。以下保留预研计划原文。

M0 先做预研，再搭正式骨架。预研分两部分：**白板渲染验证**（与 CRDT 无关）和 **CRDT 双原型对比**。全文的 CRDT 默认值暂时仍写 Loro，**以对比结果为准**；选定后统一修订全文，并写一份 ADR 记录数据与理由。

**A. 白板渲染验证（1–2 天）**

在 WebKitGTK（Linux）、macOS WKWebView、iOS WKWebView、Android WebView 上，xyflow 放 300 个带预览 HTML 的节点，测平移缩放帧率。目标：macOS / Windows ≥ 55fps，移动端 ≥ 30fps，Linux 可接受降级。不达标则先调 LOD 策略，仍不行再考虑 Canvas 渲染远景层。

**B. Loro vs Yjs 双原型（4–6 天）**

两套原型实现**完全相同的最小功能**，只换 CRDT 层：

| | 原型 L | 原型 Y |
|---|---|---|
| 前端 | `loro-crdt`（wasm）+ `loro-prosemirror` | `yjs` + `y-prosemirror` |
| Rust 侧 | `loro` crate | `yrs` crate |
| 撤销 | Loro `UndoManager` | `Y.UndoManager` |
| 历史压缩 | 浅快照（shallow snapshot） | 重新编码快照 + GC |
| 白板目录树 | `LoroTree` | `Y.Map`（parent 指针 + 分数索引排序） |

最小功能（两套一致）：
1. TipTap 卡片编辑器：段落、标题、嵌套列表、任务项、代码块、图片；每个块级节点带 `bid` 属性。
2. 白板文档：增删 / 拖动卡片、连线（Map 结构）。
3. Rust 侧持久化到 SQLite（快照 + 增量表，按 4.4 节结构）。
4. 两个前端实例 + Rust 之间互传 update，模拟离线后合并。
5. 本地撤销 / 重做。

为了让两套原型共用测试，原型阶段在 Rust 侧定义一个薄接口 `DocEngine`（`apply_update` / `export_since(version)` / `snapshot` / `compact` / `version`）。**选定后删除这层抽象**，直接使用选中的库，避免长期背着一个最小公分母接口。

**评判标准**（按优先级，前两项是一票否决）：

| # | 标准 | 怎么测 | 通过线 |
|---|---|---|---|
| 1 | **编辑器绑定正确性**（否决项） | 嵌套列表缩进/反缩进、跨块粘贴、拖动块、`bid` 属性保持、IME 中文输入、撤销重做各 50 次脚本化操作 + 1 小时手动试用 | 无崩溃、无内容丢失、无光标乱跳；`bid` 在任何操作后不变也不重复 |
| 2 | **并发合并正确性**（否决项） | 3 个 peer 随机离线编辑同一卡片与白板，10 万步随机操作（proptest），任意顺序、重复交换 update | 全部收敛到相同状态；ProseMirror schema 校验始终通过 |
| 3 | **移动端性能** | 在中端 Android 手机与 iPhone 上：打开 5,000 字卡片的耗时；连续输入时每次按键的处理时间；wasm 包体积 | 打开 < 150ms；按键 p95 < 8ms；包体积增量可接受（记录数值对比） |
| 4 | **存储与历史增长** | 模拟一张卡片 1 年的编辑（约 20 万次操作），比较压缩前后体积、从 SQLite 加载耗时 | 压缩后体积与加载耗时越小越好（记录数值对比） |
| 5 | **Rust ↔ wasm 互通** | Rust 侧导出的 update 在前端导入、反之亦然；版本向量 / state vector 比对 | 双向一致，无需额外转换层 |
| 6 | **生态与维护风险** | 绑定库的提交活跃度、issue 响应、已知生产用户、维护者数量 | 定性打分（高 / 中 / 低） |
| 7 | **开发体验** | 两套原型实际花费的时间、踩坑数量、API 是否顺手 | 定性记录 |

**决策规则**：
- 任一方在第 1、2 项不通过 → 直接选另一方；两方都不通过 → 暂停，重新评估编辑器方案。
- 都通过时，按第 3–7 项综合判断：**只有 Loro 在第 3、4 项上有明显优势（如性能或体积差距 ≥ 30%）时才选 Loro**；否则选 Yjs(yrs)，用成熟度换取功能（见 11.3 节）。
- 结果写成 `design/adr/0001-crdt-choice.md`，附测试数据；随后按选中的库修订第 2–6 节中所有 CRDT 相关描述。

|---|---|---|
| loro-prosemirror 年轻、单一维护方（npm 周下载量约为 y-prosemirror 的 1%） | 遇到问题要自己修；上游可能停止维护 | 锁定版本并 vendor 进仓库；预研的正确性测试作为升级回归测试；ADR 0001 写明复议条件（中文输入法、移动端远端更新耗时） |
| Loro 应用远端变更较慢（整篇重建，WKWebView p95 3–5 ms，手机估计 10–25 ms） | 多设备同时编辑同一卡片时偶有卡顿 | 个人多设备场景远端更新少；必要时改造绑定为按节点增量更新 |
| Loro 增加安装包体积（wasm 3.4 MB + 原生约 1.7 MB） | 下载与首次加载变大 | 可接受；wasm 只在前端加载一次（WKWebView 引擎加载约 90 ms） |
| 文档历史膨胀 | 存储/启动变慢 | 本地与服务端都定期折叠为完整快照（不丢历史）；单卡片文档天然有界；真机上过慢时再评估浅快照（5.3） |
| 并发创建同一子结构，一方内容被整块覆盖 | 静默丢数据（评审已复现：同时加同一标签、两台设备离线写同一天日记） | 4.5 节建模规则：可能并发创建的子容器一律 `ensureMergeable*`；编辑器绑定打补丁；M1 验收含“离线写同一天日记” |
| 压缩过头导致离线设备无法合并 | 长期离线设备回来时同步失败（评审已复现） | 不做浅快照：完整快照能导入任何副本（5.3）；M3 模拟器覆盖压缩、移除后重新加入 |
| ~~跨父节点移动是“删除 + 插入”~~ **已解决（2026-10-24，布局 3）** | 曾导致另一台设备同时对该块的修改丢失 | 块结构改存 `LoroTree`，跨父节点移动保留节点身份（4.5 规则 4）；`web/test/move-concurrent.test.ts` 覆盖缩进、反缩进、拖进别的列表、两台设备同时缩进同一块、互相移到对方下面 |
| 存储布局变更时的迁移顺序 | 2026-10-24 实际发生：开发中前端热更新到布局 3、Rust 迁移还没跑，编辑器把旧卡片显示为空并写入起始行，第一版迁移因此跳过了这些卡片（内容未丢，但看起来是空的） | 迁移改为合并（旧块在前、之后写的保留、空白起始行丢弃）并在迁移前自动做“升级前的备份”；以后改布局时，前端读取旧布局要么兼容、要么与迁移同一次发布，开发时先停 `tauri dev` 再切换 |
| 本地备份恢复与同步冲突 | 恢复无效，或覆盖掉未上传的新修改 | 恢复改为“切到历史版本、作为新编辑写回”；整库恢复后与服务端完整同步（5.4 节） |
| peer id 复用或随意生成 | 复用会产生冲突操作、损坏文档；随意生成会让版本向量无限增长 | 按“设备 + 进程角色”分配并持久保存（4.5 节） |
| WebKitGTK 白板性能 | Linux 体验差 | LOD + 编辑器数量上限；Linux 可接受降级 |
| Tauri 移动端插件缺失 | 分享、相机、后台同步 | 必要时自写 Swift/Kotlin 插件；同步只在前台进行 |
| CRDT 语义与用户预期不符（如并发编辑同段文字交错） | 少见的奇怪合并结果 | 个人笔记场景罕见；提供文档历史版本查看与回退（Loro 原生支持时间旅行；Yjs 需保存快照实现） |
| 同步 bug 导致数据损坏 | 最严重 | 服务端只追加不改写；客户端本地快照；模拟器 + 收敛校验；每个 bug 写确定性复现测试 |
| 中文搜索 | trigram 对 1–2 字查询无效 | 短查询回退 `LIKE`；后续可引入 jieba-rs / 拼音索引 |
| 恶意或有缺陷的社区插件 | 泄露或破坏笔记 | 封闭能力词表 + 用户授权 + 沙箱 + 资源限制；写入可撤销；注册表审计与吊销 |
| 插件 API 过早冻结 | 后续无法重构 | 数据模型稳定后才公开；API semver，废弃至少保留一个大版本 |
| QuickJS 性能不足 | 重计算插件卡顿 | 允许插件附带 Wasm 模块；必要时为特定能力提供宿主原生实现 |
| 签名与商店的费用和审核 | 每年固定开销；iOS 修复无法当天推送给公开用户；更新签名私钥丢失则无法再推更新 | 见 7.2：自用走 TestFlight 内部测试；私钥只放 CI 密钥库并离线备份 |
| 跨卡片块 id 重复 | 块引用指向不明确 | 粘贴到另一张卡片时重新生成块 id；块引用按 bid 解析、以 card_hint 消歧；索引检测并提示重复（4.2） |

### 11.2 关键基础组件

| 组件 | 结论 |
|---|---|
| **Figma 插件沙箱** | Figma 早期用 Realms 沙箱被发现可逃逸，之后改为 **QuickJS 编译成 Wasm** 运行插件逻辑；UI 放在 null-origin iframe，两者通过 postMessage 通信。**与第 6 节的插件方案完全一致**，是最好的先例 |
| **JSON Canvas** | Obsidian 发起的开放白板格式，MIT。用作白板的导入/导出格式 |
| **tldraw** | 生产环境必须有 license key，无 key 只能在开发模式运行；商业授权按年、价格需询价。**印证了选 xyflow（MIT）的决定** |
| **Loro** | MIT，Rust / JS(Wasm) / Swift，功能最全（富文本、可移动树、浅快照、版本控制），基准测试最快；但**没找到公开的知名生产用户**，loro-prosemirror 资料很少 |
| **Yjs / yrs** | AFFiNE、AppFlowy、DeepNotes 都用 Yjs 家族；`y-prosemirror` 最成熟 |

### 11.3 对本方案的影响

1. **没有开源项目同时做到“Tauri + 数据库 + Heptabase 式卡片白板 + 移动端”**——方向有空白，但也没有现成模板可抄，DeepNotes 和 AFFiNE 是最值得读源码的两个。
2. **CRDT 选型需重新权衡**：成熟项目清一色用 Yjs 家族，Loro 缺少生产案例。因此 M0 预研**同时**做 Loro 与 Yjs(yrs) 两套原型，评判标准与决策规则见 **8.1 节**。**结果：选定 Loro**（ADR 0001）。
3. **插件方案有 Figma 先例背书**，按原设计推进。
4. **加一项本地静态加密（可选）**：参考 Notesnook，用 SQLCipher / sqlite-multiple-ciphers 加密 `store.db`，密钥存 Keychain / Keystore。
5. **白板导出格式定为 JSON Canvas**，可以直接在 Obsidian 打开。
6. **同步保持简单**：Spacedrive v2 放弃通用 CRDT 的经历说明自研同步语义代价高；本方案“CRDT 负责合并、服务端只做中继”的分工不变。
