# ADR 0001：CRDT 选型（Loro vs Yjs）

- **状态**：已接受（2026-10-23）。中文输入法、移动端真机两项未覆盖，结果若触发下文的“复议条件”则重新评估
- **日期**：2026-10-22
- **依据**：`design/ARCHITECTURE.md` §8.1 的评判标准与决策规则；预研代码与原始数据在 `spike/`（复现方法见 `spike/README.md`），所有数字来自 `spike/results/`。

## 背景

ARCHITECTURE.md 暂定 Loro，但调研发现成熟的同类项目（AFFiNE、AppFlowy、DeepNotes）都用 Yjs 家族，Loro 缺少公开的生产案例。于是 M0 用两套功能相同、只换 CRDT 层的原型做对比：

| | 原型 L | 原型 Y |
|---|---|---|
| 前端 | loro-crdt 1.16.4 + loro-prosemirror 0.4.4 | yjs 13.6.33 + y-prosemirror 1.3.7 |
| Rust | loro 1.16.2 | yrs 0.28.0 |
| 编辑器 | TipTap 3.32（两边相同的扩展和块 id 规则） | 同左 |

**范围**：只在 Loro 和 Yjs 之间选。Automerge 按成熟度可排第二（npm 周下载量：Yjs 615 万、Loro 15.2 万、Automerge 4.5 万，2026-10 数据），但经讨论决定不纳入对比。

测试环境：Apple M4（10 核），macOS；jsdom（Node 26）用于大规模自动化测试；Tauri 2 外壳中的 macOS WKWebView（与 iOS 同一引擎）用于真实 WebView 测量。WebKit 把 `performance.now()` 精度降到 1 ms，WKWebView 数字都是整数。

## 结果

### 1. 编辑器绑定正确性（否决项）

两个副本在线协作，随机执行 15 类用户级操作（输入、回车、列表、缩进/反缩进、标题、代码块、跨块删除、粘贴、拖动块、退格合并、图片、撤销、重做），50 轮 × 60 步，每步检查 schema、块 id 唯一且不丢、两副本一致、编辑器与 CRDT 一致。

| | 问题 | 说明 |
|---|---|---|
| Loro | **0** | |
| Yjs 原版 | **60**（全部来自 1 次异常） | y-prosemirror 缺陷：用户选中某个节点（如图片）时，远端更新删掉了这个节点，`restoreRelativeSelection` 未判空直接 `NodeSelection.create` 抛异常（`sync-plugin.js:260`），该编辑器从此不再更新，与其他端分叉 |
| Yjs + 一行补丁 | **0** | 补丁见 `spike/web/patches/y-prosemirror/plugins/sync-plugin.js` |

中文输入法未自动化，见文末。

### 2. 并发合并正确性（否决项）

三副本随机断网 / 重连 / 乱序投递，200 轮 × 500 步 = **10 万步**，最后全量同步，检查收敛、schema、编辑器与 CRDT 一致。

| | 未收敛 | 其他问题 | 静默丢弃（次 / 丢失字数） |
|---|---|---|---|
| Loro | 0 | 0 | 25 / 19 |
| Yjs 原版 | **3** | 6 次异常、3 次不一致（同一缺陷） | 18 / 57 |
| Yjs + 补丁 | 0 | 0 | 22 / 62 |

白板文档（Map 结构，Rust 侧）：两边各 100 轮 × 1,000 步 = 10 万步，**均 0 次分叉**。

“静默丢弃”：并发结构编辑合并出不符合 schema 的结构（几乎都是空的 `bulletList` / `taskList` / `listItem`）时，绑定直接丢掉该节点。Yjs 会从 CRDT 里删掉（并同步给所有端）；Loro 只在编辑器里隐藏，节点仍留在 CRDT 里（从绑定的差量写回逻辑推测，之后的本地编辑可能会把它删掉，未验证）。两边丢失量同一量级，10 万步并发冲突里只丢了几十个字，不是区分点，但正式版需要处理（见“与选型无关的发现”）。

### 3. 性能

**新卡片**（4,653 字），macOS WKWebView：

| | 引擎加载 | 打开 p50 / p95 | 本地按键 p50 / p95 | 应用远端按键 p50 / p95 / max |
|---|---|---|---|---|
| Loro | 92 ms | 15–17 / 23 ms | 1 / 1–2 ms | 2 / 3–5 / 19 ms |
| Yjs | 81 ms | 12 / 13 ms | 0 / 1 ms | 0 / 1 / 3 ms |

同一张卡片在 jsdom 下（只看相对差异，精度更高）：Loro 本地按键 p95 3.9 ms、远端 p95 14.2 ms；Yjs 分别 0.97 ms、1.2 ms。**应用远端变更时 Loro 慢 5–40 倍**：loro-prosemirror 每次远端更新都用 `tr.replace(0, size, …)` 替换整篇文档（有节点缓存，但仍是全量重建），y-prosemirror 只更新变化的节点。

**一年期老卡片**（8,432 字、20 万次编辑，见第 4 项），macOS WKWebView：

| | 加载的数据 | 打开 p50 / p95 | 本地按键 p95 | 远端按键 p95 |
|---|---|---|---|---|
| Loro | 压缩后 61 KB | **20 / 24 ms** | 1 ms | 3 ms |
| Loro | 完整快照 2.2 MB | 20 / 36 ms | 1 ms | 2 ms |
| Yjs | 2.3 MB（无法压缩） | **131 / 138 ms** | 1 ms | 1 ms |

Rust 侧加载同一张老卡片（索引器每次变更后都要做）：Loro 0.4–1 ms，**Yjs 75 ms**。

**体积**：

| | 前端 | Rust 原生（size 优化、strip 后的最小程序） | 合计增量 |
|---|---|---|---|
| Loro | JS 98 KB（gzip 17 KB）+ **wasm 3.4 MB（gzip 1.14 MB）** | 2.37 MB | 约 5.8 MB |
| Yjs | JS 102 KB（gzip 32 KB） | 0.67 MB | 约 0.8 MB |

（两个原生程序都含 serde_json 和标准库，差值 1.7 MB 即两库本身的差距。）

**移动端推算**：没有真机数据。按手机 CPU 慢 3–5 倍估算：Loro 远端更新 p95 约 10–25 ms（偶有一帧卡顿），Yjs 约 3–5 ms；打开老卡片 Loro 约 60–120 ms，Yjs 约 0.4–0.7 秒。

### 4. 存储与历史增长

一张卡片编辑一年：365 天 × 550 次操作 = 20 万次（打字、退格删字或合并段落、新建段落），长到约 8,000 字后输入与删除大致平衡。两边操作序列完全相同，最终都是 8,432 字。

| | 增量日志 | 完整快照 | 压缩后 | 重置历史后 |
|---|---|---|---|---|
| Loro | 18.7 MB | 2.2 MB | **61 KB**（浅快照） | 73 KB |
| Yjs | **4.8 MB** | 2.3 MB | **2.3 MB**（GC 无法缩小） | 41 KB |

- **Yjs 的历史无法在原文档里压缩**：20 万次分散在各处的插入删除，留下的内部条目无法合并，GC 后体积不变。要缩小只能“重置历史”——把内容写进一个新文档，所有设备切换过去。这需要一套额外的协调协议（确保离线设备上的未同步修改不丢失），正是本项目想用 CRDT 避开的那类同步难题。
- **Loro 浅快照把卡片压到 61 KB（缩小 36 倍）**；中继服务端仍保留完整日志。评审补充：压缩点不能随意取，必须取所有设备都已确认的版本，否则长期离线的设备带着并发修改回来时会导入失败（已复现）。所以压缩需要知道各设备确认到了哪里（由服务端转达），但不需要切换文档，失败时也能从服务端拉完整日志兜底。
- Loro 的每条增量更大（约 95 字节 vs 约 24 字节）。正式应用对编辑做 300 ms 防抖合并，日志会定期折叠进快照，这个差距的实际影响很小。
- Rust 侧 SQLite 存储的往返、压缩、离线副本在压缩后补发增量，两边都验证通过。

### 5. Rust ↔ wasm 互通

两边全部通过：

1. JS 编辑器生成的卡片（标题、加粗/斜体、嵌套列表、任务项、代码块）和白板 → Rust 按原顺序、倒序、快照三种方式加载，内容一致；
2. JS 的版本向量 / state vector 能在 Rust 解码，差量导出正确；
3. Rust 按绑定的数据布局追加段落和标题、修改白板 → JS 编辑器正常渲染且 schema 合法；
4. JS 继续编辑后的增量回到 Rust，依然一致。

### 6. 生态与维护风险

| | Loro | Yjs |
|---|---|---|
| 绑定库 | loro-prosemirror 0.4.x，单一维护方 | y-prosemirror 1.3.x，多年生产使用 |
| 已知生产用户 | 未找到公开的知名用户 | AFFiNE、AppFlowy（yrs）、DeepNotes 等 |
| 本次发现的缺陷 | 无会导致分叉的缺陷 | 1 个会导致分叉的缺陷（一行可修） |
| 评分 | **中** | **高** |

### 7. 开发体验

- **Loro**：API 清晰；但绑定在 `setTimeout(0)` 后才把文档载入编辑器，挂载后的第一个事件循环内编辑器里还是空文档，此时的编辑会与已有内容冲突（预研中表现为两端分叉），编辑器必须在绑定完成前保持只读；绑定在 `appendTransaction` 里写 CRDT，导致**插件顺序敏感**（规范化插件必须排在它前面，否则一次操作被拆成两个撤销步骤）。Rust 侧部分 API 已标记废弃。
- **Yjs**：绑定是同步的；但渲染远端变更时持有互斥锁，**期间追加的编辑器变更会被静默丢弃**，修复类逻辑必须延后到渲染结束再提交；有 1 个崩溃缺陷。
- 两边各踩了 2 个坑，总体相当。

## 决策规则的应用

1. **否决项**：Loro 原版通过。Yjs 原版因选区崩溃在第 1 项不通过；打一行补丁后通过。补丁很小、原因明确，可以随项目维护并向上游提 PR，因此视为“Yjs + 补丁”也通过，进入下一步比较。
2. **第 3、4 项**（规则：Loro 在这两项上有明显优势、差距 ≥ 30% 时才选 Loro）：
   - 第 4 项：**Loro 压缩后小 36 倍**；Yjs 只有引入“重置历史”协议才能接近。
   - 第 3 项：各有胜负。**打开老卡片 Loro 快 6.5 倍**（WKWebView 20 vs 131 ms），Rust 侧加载快 75 倍以上；Yjs 在应用远端变更上快 3–5 倍（绝对值 1 vs 3–5 ms），安装包小约 5 MB。
   - 结论：Loro 在第 4 项和“老卡片”这一第 3 项的关键场景上都有远超 30% 的优势，满足选 Loro 的条件。
3. 第 6 项（生态）Yjs 高、Loro 中；第 7 项相当。生态风险用下面的措施缓解，不足以推翻第 3、4 项的差距。

## 决策

**选 Loro（前端 loro-crdt + loro-prosemirror，Rust 侧 loro）**，与 ARCHITECTURE.md 的原定方案一致。正式开发使用当时的最新版本（2026-10 时 Rust 侧为 1.17.1），升级前重跑预研的正确性测试。

理由：卡片笔记的卡片会被长期反复修改。Yjs 下一张编辑一年的卡片无法压缩（2.3 MB、WKWebView 打开 131 ms、Rust 索引器每次加载 75 ms），要解决就得设计“重置历史”的多设备协调协议，这正是本项目选 CRDT 想避开的复杂度。Loro 的浅快照只需要知道“各设备已确认到哪个版本”就能安全压缩（不用切换文档，失败可从服务端拉完整日志兜底），老卡片保持在几十 KB、20 ms 内打开。两种方案都需要一点跨设备信息，但 Loro 需要的简单得多。

接受的代价与缓解措施：

| 代价 | 缓解 |
|---|---|
| 安装包多约 5 MB | 对桌面和移动端都可接受；wasm 只在前端加载一次 |
| 应用远端变更比 Yjs 慢 3–5 倍（全量重建） | 个人多设备场景远端更新频率低；必要时 fork loro-prosemirror，改成按变化节点增量更新 |
| loro-prosemirror 年轻、单一维护方 | 锁定版本并 vendor 进仓库；保留本预研的正确性测试作为升级回归测试 |
| 绑定异步初始化、插件顺序敏感 | 编辑器在绑定完成前只读；规范化插件统一设高优先级；写进编码规范 |

**复议条件**（中英文输入法在 M1 编辑器开发时测，真机在 M4 移动端阶段测）：移动端真机测试中，中端手机上 Loro 应用远端变更的 p95 超过 16 ms 且无法通过增量更新优化解决；或中文输入法测试发现 loro-prosemirror 有无法修复的问题。

## 与选型无关的发现（正式实现必须处理）

1. **块 id 规范化必须覆盖合并和撤销**：两个绑定都没有 ProseMirror 节点的原生“移动”，拖动块 = 删除 + 插入，撤销时若对方编辑过被移动的副本，就会出现两个同 id 的块。解决：规范化插件对所有事务生效，重复 id 用确定性规则改名（首个出现者保留，其余改为 `id~n`），各端算出相同结果。预研中已实现并验证。
2. **合并产生不合 schema 的结构会被静默丢弃**：考虑放宽列表类节点的 content 表达式（允许为空），再由规范化插件清理空节点，把“丢弃”变成“可控修复”。
3. **修复类逻辑不要在渲染远端变更的同一事务里提交**：延后到微任务（Yjs 下是必须，Loro 下也更稳妥）。
4. **按键耗时主要随块数增长**：预研中一张卡片误生成了 1 万个空段落时，两边每次按键都明显变慢；正常卡片（几十到几百个块）没有这个问题。正式版要在中端手机上实测块数上限，并对超长卡片提示拆分。
5. **白板必须做缩放分档（LOD）**：WKWebView 中 300 张带 HTML 预览的卡片两次测量为 54–58 fps、卡顿帧 8–18%；切到仅标题稳定在 60 fps、卡顿帧不到 1%；只渲染视口内的卡片几乎没有收益；1000 张预览卡片降到 46–50 fps。
6. **数据布局由绑定决定**：Rust 侧导入器必须按绑定的布局写入（预研已验证两种布局都可行）。

### 方案评审补充（2026-10-23）

评审时用测试复现了以下问题，复现在 `spike/web/test/review.test.ts`，修复验证在 `review-fix.test.ts`。它们是**使用 Loro 时必须遵守的规则**，已写入 ARCHITECTURE.md 4.5、5.3、5.4 节。

7. **并发创建同一子容器会整块覆盖**（已复现）：两台设备在 Map 的同一个键下各自 `setContainer` / `getOrCreateContainer`，合并后只保留一个容器，另一方写入的内容全部丢失。场景：同时给卡片加同一个标签；两台设备离线写同一天的日记（日记用确定性 id，loro-prosemirror 建根结构时用的是普通容器），**一台设备写的日记整段消失**。修复（已验证）：可能并发创建的子容器一律用 `ensureMergeable*`；vendor 的 loro-prosemirror 把节点的 `attributes` / `children` 改为 mergeable 容器。注意 mergeable 容器删除键后内容仍保留，再次创建时会重新出现。
8. **压缩过头导致离线设备无法合并**（已复现）：浅快照裁掉的历史如果被离线设备的并发修改依赖，导入直接失败。修复（已验证）：只压缩到所有设备都已确认的版本；导入失败时从服务端拉完整日志重建。
9. **本地备份恢复与同步冲突**（推理得出，未写测试）：备份里的同步游标也是旧的，直接替换数据库后同步会把新内容拉回来；若服务端没有新内容，则新修改被覆盖丢失。修复：恢复卡片旧版本改为“切到历史版本、算出差异、作为新编辑写回”；整库恢复后与服务端完整同步。
10. **永久删除只作用于本机**（推理得出）：其他设备和服务端会把文档带回来。修复：workspace 文档记录已永久删除的 `doc_id`，各设备据此删除并拒绝再导入，服务端同步删除。
11. **peer id 管理**（推理得出）：同一设备上前端和 Rust 的文档副本必须用不同 peer id，且同一 id 不能被两个同时活跃的副本共用；也不能每次打开都随机生成，否则版本向量无限增长。修复：按“设备 + 进程角色”分配并持久保存。
12. **不用自动补内容的编辑器插件**：如 TipTap 的 trailingNode，各设备各补一次，合并后重复。预研中已关闭，未单独测试。

## 修订记录

- 2026-10-23 方案评审：补充第 7–12 条（并发创建子容器、压缩点、备份恢复、永久删除、peer id、自动补内容插件），修正“每台设备可独立压缩”的说法。选型结论不变。

- 初稿曾倾向 Yjs。当时的一年期存储数据被预研代码的缺陷污染：测试只新建段落、从不合并，卡片里积累了 10,113 个块（其中 6,272 个空段落），体积主要是块结构开销，掩盖了 Loro 浅快照的优势，也让“按键耗时随历史增长”看起来像普遍现象。修正操作组合后重跑，得出本版结论。
